# Osseo AI · DXA-QC — сервис ИИ для контроля качества денситометрии

Локальный сервис, который принимает DICOM-исследования DXA (поясничный отдел позвоночника, проксимальный
отдел бедра), определяет анатомическую область, оценивает качество укладки/позиционирования, называет тип
нарушения и **показывает, почему**: измеренный угол оси, видимость гребней подвздошных костей, отступы в
миллиметрах, найденные артефакты. Результат — таблица CSV/XLSX по контракту ТЗ, доп. серии DICOM
(визуализация + DICOM SR) и веб-интерфейс.

## 1. Возможности и ограничения

| Требование ТЗ | Реализация |
|---|---|
| Область и проекция | «Поясничный отдел позвоночника» / «Проксимальный отдел бедра» (закрытый список организатора; сторона — в доп. колонке `laterality`). Определяется по изображению, теги не нужны. Точность на групповой CV: 100 % |
| Бинарный класс качества | `quality_class` 0/1 + `quality_prob` ∈ [0;1] — имя и диапазон колонки согласованы с организатором (нужна для ROC-AUC) |
| Типы нарушений (мультилейбл) | точные метки организатора через «;», пусто при отсутствии. Позвоночник: «Некорректная укладка», «Не выровнена ось позвоночника», «Присутствуют посторонние предметы». Бедро: «Некорректная укладка», «Некорректная область интереса». Внутренние коды — в `violation_codes` |
| Отчёт | `results.csv` и `results.xlsx`: первые 8 колонок — строго по п. 2.5 ТЗ и в том же порядке |
| Визуализация нарушения | PNG + DICOM Secondary Capture: ось позвоночника, контуры артефактов, ориентиры бедра, линии отступов 3/2 см |
| DICOM SR | Basic Text SR с вердиктом, нарушениями и измерениями, привязан к исходному изображению |
| Веб-интерфейс | `http://localhost:8000/` — загрузка ZIP/DICOM, прогресс, таблица, детальная панель; без внешних ресурсов |
| Пакетная обработка | папка или ZIP (вложенные ZIP, кириллица cp866, защита от zip-slip и zip-бомб) |
| Устойчивость | ни один файл не останавливает пакет: строка `Failure` + `error_code` + `error_message` |
| Воспроизводимость | CPU-инференс, фиксированные сиды, сортированный обход, UID доп. серий выводятся из исходного UID; проверено тестом и двумя полными прогонами |
| Локальность | сеть не используется; пакетный режим запускается с `--network none` |
| Скорость | ≈0.1 с на изображение, < 1 с на исследование на CPU ноутбука (лимит ТЗ — 180 с на исследование) |

Ограничения (честно):
* обучающая выборка — 100 исследований / 249 размеченных изображений одного аппарата (GE Lunar Prodigy Advance);
  переносимость на Hologic и др. не проверена — сервис пометит низкую `region_confidence`, но не откажет;
* редкие классы (укладка позвоночника — 6 позитивов, ROI бедра — 7) оцениваются с широкими ДИ;
* входные DICOM не содержат нанесённых ROI, поэтому «корректность разметки» оценивается как корректность
  кадра для размещения ROI (охват, отступы, ориентиры), а не как проверка линий оператора;
* эксперты не считают ошибкой наклон оси при сколиозе — модель учитывает кривизну, но на границе ошибается;
* результат ИИ требует подтверждения специалистом.

```

│   ├── geometry.py        объяснимые измерения (ось, гребни, артефакты, малый вертел, отступы)

│   ├── model.py           роутер области + ансамбли по критериям + сборка quality_prob
│   ├── pipeline.py        пакетная обработка, дедупликация пикселей, сводка
│   ├── explain.py         оверлей, DICOM Secondary Capture, DICOM SR

│   ├── report.py          CSV/XLSX без внешних библиотек
│   ├── api.py, cli.py     HTTP API и командная строка
│   └── static/index.html  веб-интерфейс (офлайн)
├── train.py               обучение + честная валидация (одна команда)
├── leakage_check.py       негативный контроль: перемешанные метки → AUC≈0.5

├── review_candidates.py   список меток на перепроверку экспертом (уверенные OOF-расхождения)
├── external_validation.py внешняя проверка на другом аппарате (Hologic, открытый набор Ramathibodi)
├── labels/image_labels.csv  проверенная привязка «изображение → область → метки Excel»
├── models/bundle.joblib   обученная модель      weights/  веса энкодера (sha256 проверяется при сборке)
├── reports/               validation_metrics.json, oof_predictions.csv, leakage_check.json, full_batch_summary.json, experiments/
├── tests/                 33 теста (юнит + сквозные + API + враждебные входы + словарь организатора + динамика)
├── Dockerfile, run.sh, requirements.txt, requirements-lock.txt, requirements-test.txt
└── docs/                  USER_GUIDE, DEPLOYMENT, TRAINING, APPROACH (для презентации)
```

## 3. Системные требования

| | Минимум | Рекомендуется |
|---|---|---|
| CPU | 2 ядра x86-64 | 8 ядер |
| RAM | 2 ГБ | 4 ГБ |
| GPU | не требуется | не требуется (на стенде 2×H200 сервис работает на CPU) |
| Диск | 2 ГБ (образ) + место под результаты | 10 ГБ |
| ПО | Docker 24+ | Docker 24+ |

GPU сознательно не используется: изображения 250×300 px, полный цикл < 1 с, а CPU-инференс детерминирован
(повторные прогоны на одной машине совпадают до последнего знака; между разными CPU возможны расхождения
на уровне погрешности float, не влияющие на класс). Все версии зафиксированы в `requirements*.txt` и `Dockerfile`.

## 4. Сборка и запуск

```sh
./run.sh build                                  # сборка образа osseo-dxaqc:1.0.0
./run.sh batch /path/to/test_set /path/to/out   # папка или .zip → out/results.csv, results.xlsx, additional_series.zip
./run.sh serve 8000                             # API + веб-интерфейс на http://127.0.0.1:8000
./run.sh test                                   # тесты внутри образа
```

Без Docker: `pip install -r requirements.txt -r requirements-lock.txt --extra-index-url https://download.pytorch.org/whl/cpu`,
затем `python -m dxaqc.cli --input IN --output OUT` или `uvicorn dxaqc.api:app`.


## 6. Формат входа и выхода

Вход: папка или ZIP с DICOM в любой вложенности; имена и расширения не важны; не-DICOM файлы (xlsx, txt…)
пропускаются, нечитаемые DICOM попадают в отчёт как `Failure`. Персональные данные не читаются.

Выход — одна строка на каждый DICOM-файл с изображением:

| Колонка | Значение |
|---|---|
| `path_to_study` | папка исследования относительно входа: определяется по StudyInstanceUID, папки-обёртки архива и вложенные папки серий не путаются с исследованием (для плоской структуры — путь файла) |
| `study_uid`, `image_uid` | StudyInstanceUID / SOPInstanceUID **как в файле** (в данных организатора UID нарушают синтаксис DICOM — не «чиним») |
| `anatomical_region` | «Поясничный отдел позвоночника» / «Проксимальный отдел бедра» |
| `quality_class` | 0 — качественное, 1 — есть нарушение (для `Failure` — 1: исследование нельзя принять без просмотра) |
| `violation_type` | метки из закрытого списка организатора через `;`; пусто при отсутствии нарушений и для строк `Failure` (причина — в `error_code`) |
| `processing_status`, `time_of_processing` | Success/Failure, секунды |
| `quality_prob` | вероятность нарушения [0;1] (колонка согласована с организатором) |
| *доп.:* `laterality`, `violation_codes`, `violation_scores`, `violation_description`, `measurements`, `region_confidence`, `pixel_mm`, `pixel_mm_source`, `duplicate_of`, `error_code`, `error_message`, `path_to_file`, `explanation_png` | вероятность, объяснение, измерения, диагностика |

Флаг `--strict-columns` оставляет только 8 колонок ТЗ + `quality_prob`. Точные пиксельные копии внутри пакета (в обучающем
наборе их 247 из 499) получают идентичный вердикт, ссылку `duplicate_of` и ту же визуализацию `explanation_png`.
Служебные файлы (`DICOMDIR`, `.xlsx`, `.pdf`, изображения-превью) строк не порождают: строка = DICOM-изображение.
Если вход целиком недоступен (нет пути, архив не открывается), всё равно создаётся `results.csv` со строкой
`Failure / BATCH_INPUT_ERROR` — организатор никогда не остаётся без таблицы.

## 7. Модель, пред- и постобработка

1. **Чтение**: pydicom → 8 бит, MONOCHROME1 инвертируется, RGB/многокадровые приводятся, пустые кадры → `Failure`.
2. **Масштаб**: в данных нет PixelSpacing. Организатор сообщил нативный шаг сканера (0.6 мм по X, 1.05 мм по Y),
   но экспортированные DICOM уже пересчитаны в квадратный пиксель: `ExposedArea (0040,0303)` ÷ размер кадра даёт
   0.60 мм по X и 0.607 мм по Y на всех 200+ кадрах с этим тегом (180×193 мм ↔ 300×318 px), а при 1.05 мм/пикс
   поясничный скан имел бы высоту 33 см, что анатомически невозможно. Поэтому используется 0.607 мм/пикс —
   это делает проверяемым критерий «3 см / 2 см». Для составных исследований тег описывает
   не кадр — тогда берётся константа аппарата (`pixel_mm_source` виден в отчёте).
3. **Область**: логистическая регрессия на эмбеддинге ResNet18; левое бедро зеркалится к канонической ориентации.
4. **Измерения** (`geometry.py`): трекинг оси позвоночника динамическим программированием → угол, кривизна
   (сколиоз ≠ ошибка укладки); доля кости в зонах гребней подвздошных костей; top-hat/насыщение для
   металла и белья; ось диафиза, выступ малого вертела относительно хорды «диафиз→шейка», отступы в мм.
5. **Критерии**: на каждый тип нарушения — среднее RandomForest + LogReg на 6–11 профильных измерениях
   + LogReg на эмбеддинге. **quality_prob** = среднее (noisy-OR критериев, RF по всем измерениям, CNN-LogReg).
   Для критерия оси обучающая выборка дополняется **синтетическими нарушениями**: качественные снимки
   поворачиваются на 7–12° (метка известна по построению: порог ТЗ — 5°). Они участвуют только в обучении
   и только вместе со своим «родителем» (в оцениваемый фолд не попадают), оценка — всегда на реальных снимках.
   Эффект измерен парно на тех же фолдах: AUC позвоночника 0.785 → 0.802 во всех трёх повторах
   (`reports/exp_baseline_no_synthetic.json` vs `reports/validation_metrics.json`); прирост внутри ДИ.
6. **Постобработка**: пороги по F1 из out-of-fold предсказаний; если класс 1, а ни один критерий не прошёл
   порог — называется наиболее вероятный; металлоконструкция в бедре (≥1.5 % насыщенных пикселей) — правило:
   класс 1, метка «Некорректная область интереса» (ближайшая из закрытого списка), причина — в `violation_description`.

Почему так: 249 изображений недостаточно для end-to-end нейросети (линейная проба на CNN-эмбеддинге даёт
AUC ≈ 0.5 по оси позвоночника — `reports/experiments/cnn_linear_probe.txt`), а измерения, повторяющие логику
методических рекомендаций, работают заметно лучше на тех же фолдах (`reports/experiments/`) и сразу
являются объяснением для врача.

## 8. Качество (групповая 5-fold CV × 3 повтора, пороги выбраны вне оцениваемого фолда)

См. `reports/validation_metrics.json` (95 % ДИ — кластерный бутстрап по исследованиям) и `docs/APPROACH.md`.

| Срез | n (наруш.) | ROC-AUC [95% ДИ] | PR-AUC | F1 [95% ДИ] | Чувств. | Специф. | Сбал. точн. |
|---|---|---|---|---|---|---|---|
| Позвоночник | 99 (32) | 0.81 [0.72–0.90] | 0.65 | 0.66 [0.52–0.78] | 0.72 | 0.78 | 0.75 |
| Бедро (оба) | 150 (41) | 0.78 [0.67–0.87] | 0.65 | 0.52 [0.36–0.65] | 0.51 | 0.83 | 0.67 |
| **Всего** | 249 (73) | 0.79 [0.72–0.86] | 0.64 | 0.58 [0.48–0.68] | 0.60 | 0.81 | 0.70 |

| Тип нарушения (метка организатора) | позитивов | ROC-AUC [95% ДИ] | F1* |
|---|---|---|---|
| Позвоночник · Некорректная укладка | 6 | 0.86 [0.63–1.00] | 0.67 |
| Позвоночник · Не выровнена ось позвоночника | 10 | 0.80 [0.69–0.91] | 0.43 |
| Позвоночник · Присутствуют посторонние предметы | 17 | 0.90 [0.78–0.98] | 0.79 |
| Бедро · Некорректная укладка | 36 | 0.73 [0.60–0.85] | 0.52 |
| Бедро · Некорректная область интереса | 7 | 0.94 [0.83–1.00] | 0.60 |

macro-F1 по типам нарушений*: позвоночник 0.63, бедро 0.56. Определение области: 100 % на групповой CV (`region_router_cv_accuracy`).

\* F1 по отдельным типам посчитан с порогом, выбранным на объединённых OOF-предсказаниях, — это оптимистичная оценка; AUC от порога не зависит. F1 итогового класса — честный (порог из внутренней CV).

Контроль на утечку (`leakage_check.py` → `reports/leakage_check.json`): метки переставлены между исследованиями целыми блоками — тот же протокол даёт AUC 0.48 (позвоночник) и 0.47 (бедро), т. е. случайность, как и должно быть.
Пакетный прогон всех 499 DICOM обучающего архива (`reports/full_batch_summary.json`): 100 % Success, ≈0.1 с/изображение, < 1 с на исследование (12-ядерный ноутбук, CPU); запуск из папки и из ZIP дают идентичные классы, типы нарушений и score (расхождение 0.0).

Для сравнения: прежний baseline проекта (ResNet18 на уровне исследования) — ROC-AUC 0.59, F1 0.53; та же схема без
синтетических поворотов — 0.78 / 0.56 (`reports/exp_baseline_no_synthetic.json`); до признаков верхней зоны
артефактов — 0.79 / 0.57 (`reports/exp_before_top_artifact.json`).

**Внешняя проверка на другом аппарате** (`reports/external_ramathibodi.json`, Hologic, 20 пациентов, в обучении не
используется): область определяется в 100 % после автокоррекции полярности; измерения переносятся слабо
(AUC 0.58–0.72, на снимках нанесены ROI и другой масштаб) — сервис настроен на экспорт GE Lunar, что совпадает
с ответом организатора «в наборах данных будет единый вариант аппарата».

## 9. Известные ошибки и их обработка

| `error_code` | Причина | Поведение |
|---|---|---|
| `DICOM_PARSE_ERROR` | файл не DICOM / повреждён | строка `Failure`, пакет продолжается |
| `NO_PIXEL_DATA` | SR, Presentation State, DICOMDIR | `Failure` |
| `PIXEL_DECODE_ERROR` | сжатие без кодека (JPEG2000/JPEG-LS) | `Failure`; в образ можно добавить `pylibjpeg` |
| `UNSUPPORTED_PIXEL_LAYOUT` / `UNSUPPORTED_IMAGE_SIZE` / `EMPTY_IMAGE` | нестандартный или пустой кадр | `Failure` |
| `INTERNAL_ERROR` | непредвиденное исключение | `Failure` + трассировка в `errors.log` |
| `BATCH_INPUT_ERROR` | вход недоступен / архив не открывается | таблица из одной строки `Failure`, код возврата 2 |
| `LOW_REGION_CONFIDENCE` (предупреждение) | изображение не похоже на позвоночник/бедро (другая область, другой аппарат) | обрабатывается, помечается для просмотра |
| `NON_CONFORMANT_UID_PRESERVED` (предупреждение) | UID с ведущими нулями | обрабатывается, UID сохраняется как есть |
| `EXPLANATION_FAILED` (предупреждение) | не удалось построить доп. серию | вердикт сохраняется |
