## Первый цикл проверок метрик — 24.09.2026

Полный `scripts/verify.sh` завершился успешно: frontend lint, 50 frontend-тестов, TypeScript/Vite build, 50 backend-тестов (2 skipped), 115 competition-тестов (5 skipped). Контейнерный `competition/run.sh test` прошёл: 115 passed, 5 skipped; контейнерный синтетический batch прошёл strict-проверку на 1/1 входе. Дополнительно full-batch container test подтвердил обработку всех 499 входов, но strict submission gate упал на 19 отсутствующих типов. Входные DICOM содержат невалидные UID; pydicom выдал предупреждения. Никакой из этих тестовых прогонов не является клинической проверкой.

По полному датасету организатора отдельно пересчитаны метрики итогового текста `violation_type`: [сводка и протокол](ORGANIZER_DATASET_METRICS_2026_09_24_RU.md), [машинный отчёт](../competition/reports/organizer_dataset_metrics_2026_09_24.json). На 249 размеченных уникальных изображениях study-held-out OOF: общий F1 0,580, ROC-AUC 0,801, macro-F1 пяти критериев 0,488. Официальный тип оси позвоночника найден в 1 из 10 размеченных случаев; 34 положительных OOF строк остались без типа. Поставляемые веса на тех же обучающих снимках дали F1 0,967 и AUC 1,000 — это диагностическая оценка на данных обучения, непригодная как оценка обобщения. Три DICOM из отдельной папки `Для теста` обработаны 3/3, strict таблица валидна, но ответов для расчёта точности в папке нет. Два новых теста скрипта оценки прошли; полный suite после этого добавления повторно не запускался.

Сверены сохранённые study-held-out отчёты `data/specialists/reports/qc-v3/metrics.json` и парный benchmark `data/specialists/benchmarks/paired-v3/metrics.json`. В общей тестовой части QC v3 для `convnextv2-bce-v2` — 46 изображений (19 исследований; 10 положительных и 36 отрицательных): ROC-AUC **0,642**, AP **0,437**, balanced accuracy **0,581**, F1 **0,390**, recall **0,80**, specificity **0,361**. Confusion matrix: TN=13, FP=23, FN=2, TP=8 — рабочая точка сохраняет recall ценой большого числа ложных тревог. 95% bootstrap CI по исследованиям для ROC-AUC: **0,374–0,846**, для AP: **0,162–0,726**. При десяти позитивных случаях неопределённость велика.

В отдельном парном benchmark на той же общей тестовой части: `joint_frozen_cnn` — AUC 0,642 / F1 0,390; `regional_finetuned_cnn` — AUC 0,639 / F1 0,462; `validation_selected_fusion` — AUC 0,833 / F1 0,462; `hybrid_refit` — AUC 0,869 / F1 0,432. Пороговые варианты выбраны по validation, но все числа основаны на малом ранее просмотренном внутреннем test; трактовать их как независимый результат нельзя. Высокий AUC отдельных гибридных вариантов при неизменном низком F1 показывает, что один подбор порога может улучшить рабочую точку, но сам по себе не доказывает улучшение ранжирования или обобщения.

Региональные fine-tune-результаты нельзя ранжировать по одному test score: позвоночник имеет 7 позитивов из 19 тестовых исследований; бедро — всего 3 позитива из 27 снимков. Для бедра AUC 0,917 у single-view варианта и 0,681 у dual-view варианта имеют слишком широкую неопределённость, чтобы заключать о преимуществе single-view. У обоих вариантов specificity лишь 0,50 на выбранных порогах. В обучении виден разрыв: у общего BCE ROC-AUC 0,988 на train против 0,642 на test, у ASL 0,995 против 0,642; это сигнал переобучения/сдвига, а не повод выбирать модель по train.

### Решение по следующим экспериментам

1. **Сначала проверить релизный выход**: повторить полный архив на актуальном коде и прогнать строгий валидатор; отдельно сверить каждую положительную строку с закрытым перечнем `violation_type`. Критерий — ноль ошибок схемы и ноль положительных строк без согласованного типа; приложить JSON валидации и manifest входов/выходов.
2. **Зафиксировать основной baseline и не подбирать параметры на test**: повторно считать парные OOF предсказания фиксированного study-group протокола; сравнивать ROC-AUC/AP как ранжирование и F1/recall/specificity/balanced accuracy только при пороге, выбранном внутри train/validation. Сохранять идентификаторы групп и bootstrap по исследованиям.
3. **Разобрать 23 FP гибрида** по регионам и видам разметки на review-пакете, не меняя меток задним числом. Критерий — причины ошибок имеют категории (качество изображения, анатомический регион, неоднозначная метка, артефакт/техника, прочее) и экспертный статус; каждый исправленный label — с происхождением и аудитом.
4. **Сравнить простые способы регуляризации** (снижение ёмкости/заморозка backbone, более сильная study-safe аугментация, веса классов или focal/ASL) на одинаковых внешних study-folds. Одновременно вести train/validation gap и калибровку. Критерий продвижения — улучшение OOF AP или balanced accuracy без заметного ухудшения sensitivity и без расхождения результатов между повторами; единичный тестовый сдвиг не считать победой.
5. **Увеличить опору на положительные метки и согласие экспертов**, особенно для бедра и редких типов нарушения. До этого представлять региональные метрики вместе с support и ДИ, а при недостаточном классе писать «оценка неустойчива/не определена», не заявлять лидерство модели.

Артефакты: [QC v3 summary](../data/specialists/reports/qc-v3/metrics.json), [paired v3 summary](../data/specialists/benchmarks/paired-v3/metrics.json). Предсказания и исходные медицинские данные остаются локальными; этот документ фиксирует агрегированные показатели и их ограничения.

## Первый разбор OOF-ошибок — 24.09.2026

Создан локальный пакет визуальной проверки по `decision_v3_pipeline_cv_oof.csv`: один study-held-out OOF проход, 249 изображений, изображения взяты из учебного архива. В пакет вошли 72 расхождения с текущей разметкой; метки не изменялись. Область/сторона правильно маршрутизированы на всех 249 примерах. Это не независимая оценка: OOF отчёт уже использовался внутри команды, а экспертная переоценка карточек ещё не выполнена.

- **34 бинарных положительных результата без типа нарушения**: по имеющимся меткам 27 относятся к quality=0, 7 — к quality=1. Значит, это одновременно источник ложных тревог и отдельная проблема типизации для части настоящих положительных случаев. Не подставлять случайный тип: это сделает таблицу формально валидной ценой ложного клинического объяснения.
- **Ошибки бедра:** 10 пропусков `hip_position_rotation` (6 при предсказанном quality=0, 4 при quality=1, но без этого типа) и 21 ложное срабатывание относительно текущей разметки (17 при quality=0, 4 при quality=1 с другим типом). Это приоритетный класс для проверки разметки и правила ротации; оценка по малой региональной тестовой выборке не даёт основания менять порог напрямую.
- **Ось позвоночника:** 10 OOF случаев, где разметка `spine_axis=1`, а тип не выведен; в 5 из них бинарный класс при этом совпадает с positive. Значит, бинарный score сам по себе не заменяет классификатор конкретного критерия.

Следующий безопасный шаг качества — экспертно просмотреть карточки прежде, чем менять пороги: подтвердить/опровергнуть текущие критерийные метки, отметить техническое качество, проекцию и причину неоднозначности. Затем повторить сравнение гипотез порога/калибровки внутри study-held-out folds, а не подбирать порог по этим 249 итоговым прогнозам. Текущий пакет находится в `data/specialists/review/decision-v3-errors-2026-09-24/` (HTML с медицинскими изображениями, JSON с путями и сводкой; папка исключена из Git). Его можно заново создать для любого одного study-held-out OOF запуска: `make review-model-errors ERRORS_DATASET='/path/to/Исследования' ERRORS_OUTPUT=data/specialists/review/my-run`.

Для будущих запусков диагностический сборщик дополнительно сохраняет правильную и предсказанную область в каждой карточке и считает ошибку роутера отдельной причиной. Сводка указывает состав положительных результатов без типа по референсному классу и области; это помогает отличить бинарные ложные тревоги от пропусков типизации. Медицинские изображения и индивидуальные пути не входят в Git.

## Оценка предложенных репозиториев как основы

Проверены README и видимые лицензии указанных GitHub-репозиториев 24.09.2026. «Готовый проект» здесь означает исследовательский код/модель для другой постановки, а не готовую проверенную часть нашего DXA QC. До включения в поставку нужно закрепить commit, проверить лицензию кода и весов отдельно, зависимости, формат входа и воспроизводимость.

| Проект | Что фактически заявлено в репозитории | Пригодность для нашего DXA QC | Решение |
|---|---|---|---|
| [xrayto3D-morphometry](https://github.com/naamiinepal/xrayto3D-morphometry) | Вычисляет ориентиры/морфометрию из **3D сегментированного объёма**, пример использует NIfTI-маску; готового веса модели для 2D DXA в репозитории нет. | **Не подходит для нашего входа DXA**: нет модели, принимающей денситометрический кадр и выдающей требуемые ориентиры. | Не скачивать и не подключать в этот проект. Отметить как неподходящий; пересмотр возможен только при появлении отдельной проверенной 3D-реконструкции из DXA и разрешённого формата весов. |
| [DXA-to-3D](https://github.com/EmmanuelleB985/DXA-to-3D) | Оценивает форму позвоночника из AP DXA; вес 139 МБ уже есть в `data/specialists/weights/dxa_to_3d.pt`, SHA-256 `9e86fb66…120e2c3`. | Модальность DXA подходит, но цель — форма позвоночника, не конкурсный QC, детекция бедра или нумерация Th12–L5. CPU-smoke на одном организаторском lumbar DICOM с текущим 224-пиксельным preprocessing проекта выполнился за 3,7 с и вернул вектор из 1254 конечных чисел. Это проверяет запуск checkpoint, но не воспроизводит подтверждённый upstream preprocessing и не подтверждает координаты/порядок кривых. | Оставить только как экспериментальную модель формы позвоночника. Она не меняет итоговый QC. Для переноса на ПК выполнить `make dxa-to3d-model` и `make dxa-to3d-verify`: загружаются только кодовый архив и этот checkpoint, оба проверяются по SHA-256, веса не коммитятся в Git. |
| [YUHS-VERTE-X](https://github.com/nkhong84/YUHS-VERTE-X) | Классифицирует риск переломов/остеопороза на **боковых рентгенограммах и DXA VFA**; в репозитории не найден публикуемый inference checkpoint. | **Не подходит для нашего конкурсного контракта**: иная плоскость/цель, а входные кадры — поясничная и бедренная DXA для проверки укладки/артефактов/ROI. | Не скачивать и не подключать; отметить как неподходящий для текущего проекта. |
| [SpineFM](https://github.com/sjsimons/SpineFM) | Сегментация/идентификация тел позвонков на обычных рентгенограммах; требует отдельных весов и base SAM, лицензия GPL-3.0. | **Не подходит для прямого DXA inference**: домен снимка иной; перенос и качество на денситометрии не подтверждены. | Не хранить веса в проекте и не включать в конкурсный inference. |
| [TotalSegmentator](https://github.com/wasserth/TotalSegmentator) | Сегментирует CT/MR объёмы; принимает серию DICOM-срезов, лицензия Apache-2.0 для открытых задач. | **Не подходит для плоских DXA-денситометрических изображений**: DICOM-контейнер не означает, что пиксели являются CT/MR-томографией. | Не хранить веса CT/MR-моделей в проекте. |
| [TorchXRayVision](https://github.com/mlmed/torchxrayvision) | Классификаторы/признаки для рентгенограмм **грудной клетки**; лицензия библиотеки не переносится автоматически на каждый baseline checkpoint. | **Не подходит как готовая модель денситометрии**: другая анатомия и другие выходные метки. | Не хранить веса моделей грудной клетки в проекте. |

**Практический вывод:** из перечисленного готовый checkpoint для AP DXA есть у DXA-to-3D; он уже скачан и проверен по SHA-256. YUHS-VERTE-X исследует также DXA VFA, но боковую проекцию и другую задачу; публичный inference checkpoint не найден ни в дереве GitHub, ни в релизах/README. xrayto3D-morphometry не публикует вес модели. Веса SpineFM, TotalSegmentator и TorchXRayVision были ошибочно скачаны при расширительном толковании запроса, затем удалены; в проекте их нет. Для улучшения локализации бедра потребуется отдельный детектор/модель ориентиров, обученная на DXA, и экспертные координаты.

24.09.2026 модель DXA-to-3D дополнительно проверена на **12 поясничных DICOM из 12 исследований** (по шесть с текущей меткой качества 0 и 1): SHA-256 веса совпал, все выходы конечные, размер вектора `[1, 1254]`, медиана CPU-инференса при четырёх потоках — **4,03 с/изображение** после однократной загрузки модели. Препроцессинг выполнен проектным `image_tensor(224)`. Опубликованный upstream inference описывает иной путь (512 пикселей, grayscale, CLAHE), несовместимый по каналам с этим checkpoint; исходный обучающий препроцессинг и смысл 1254 координат остаются неустановленными. Поэтому F1/AUC по конкурсным типам из этого выхода получить нельзя и в основной QC-вердикт он не подключён. Протокол и сводка: [`external_repos_runtime_2026_09_24.json`](competition/external_repos_runtime_2026_09_24.json).

- [ ] Показаны честные метрики с доверительными интервалами, скорость и требования к ресурсам.
- [ ] Продемонстрированы два региона, несколько нарушений и один отказной сценарий.
- [ ] Показаны ограничения и реалистичный план пилота; интерфейсные функции не подменяют доказательство точности.

## Что нельзя обещать по текущим доказательствам

- Первое место или превосходство над командами: нет весов оценивания, закрытых метрик и данных о соперниках.
- Клиническую пригодность либо независимую точность: нет внешней клинической проверки.
- Полное анатомическое покрытие: локализация Th12, тазовых краёв и части ориентиров бедра экспертно не подтверждена.
- Готовность результата 1.9 к отправке: строгая проверка таблицы этого релиза провалена.
- Скорость на H200: зафиксированы локальные CPU-замеры, не замер финального стенда.
