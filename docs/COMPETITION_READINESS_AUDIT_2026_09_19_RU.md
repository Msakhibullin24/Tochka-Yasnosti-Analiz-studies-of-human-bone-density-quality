В ТЗ F1 и ROC-AUC прямо названы приоритетными. Обнаруживать примерно половину нарушений бедра — основной конкурентный недостаток. По отдельным критериям: ось позвоночника — чувствительность 0.30 (7 пропусков из 10), позиционирование/ротация бедра — 0.472 (19 из 36). Даже эти результаты по типам оптимистичны из-за выбора порогов на оцениваемых OOF-предсказаниях.

Положительные стороны: разбиение по исследованиям, дедупликация, внутренний выбор порога бинарного качества, кластерные доверительные интервалы, отрицательный контроль с перестановкой меток. Синтетические изображения следуют за родительским изображением только в обучающие фолды. Это существенно сильнее случайного разбиения исходных файлов.

Ограничения: независимость пациентов между исследованиями не подтверждена; признаки разрабатывались с просмотром всего набора; редкие классы имеют лишь 6–7 положительных примеров. Перестановочный контроль не исключает все виды утечки или переобучение исследовательских решений. Внешний отчёт Ramathibodi проверяет роутер и отдельные измерения на 20 пациентах, прямо исключая валидацию финального классификатора. Его нельзя представлять как подтверждение качества модели на Hologic.

## Приоритетные проблемы

### P0: валидация не оценивает точный итоговый алгоритм

`competition/train.py:225–251` оценивает `GroupModel.predict` и отдельные пороги критериев. `competition/dxaqc/pipeline.py:116–123` дополнительно:

- убирает все типы нарушений при общем классе 0;
- выбирает максимальный тип принудительно, если общий класс 1, но ни один критерий не достиг порога;
- повышает класс и score до минимум 0.99 при эвристике металлического импланта.

Эти преобразования не проходят через опубликованную CV. Пороги типов выбираются на тех же объединённых OOF, по которым считается их F1. Кроме того, итоговая метрика использует усреднение/голосование трёх повторов CV, тогда как сдаётся один bundle, обученный на всей выборке. Это допустимый исследовательский результат, но не точная оценка выдаваемого CSV.

Исправление: один общий механизм формирования решения для CV и API; внутренний выбор всех порогов; оценка фактически выдаваемых официальных меток после всех правил; метрики отдельно по повторам и доверительные интервалы. Сохранять OOF по каждому критерию и конфигурацию/хеш кода. При улучшении выбирать модель по заранее определённому протоколу, не по повторным взглядам на контрольную выборку.

### P1: кэш учитывает пиксели, но игнорирует физический масштаб

`competition/dxaqc/pipeline.py:178–205`: ключ — только `pixel_sha256`. Воспроизведено на двух DICOM с одинаковыми пикселями и PixelSpacing 0.4 / 1.2 мм. Отдельный анализ дал высоту 120 / 360 мм, пакет — 120 / 120 мм, хотя в CSV масштабы остались 0.4 / 1.2. Значит, измерения и потенциально вердикт зависят от порядка файлов. Ключ должен учитывать все входы, влияющие на решение. Производные DICOM нужно формировать с привязкой к каждому исходному объекту: сейчас дубликат также получает ссылку на PNG первого изображения, а отдельные SC/SR для него не создаются.

### P1: повреждённые архивы могут потеряться из отчёта

Воспроизведено через API: корректный внешний ZIP с повреждённым `nested.zip` → `status=finished`, `files=0`, `failure=0`, `error=null`. Комментарий в `run_batch` обещает Failure-строку, но `discover` отбрасывает такой ZIP. `safe_extract` также перехватывает ошибки отдельных членов архива без структурированного журнала этих ошибок.

При исключении уровня пакета API выставляет `failed`, но CSV не пишет (`api.py:60–61`), в отличие от CLI. Проверено с уменьшенным в тестовом процессе лимитом размера архива: `failed`, `archive is too large`, скачивание CSV → HTTP 409. Исправление: единая политика отчётности для CLI/API и учёт каждого исключённого входа; пустой результат должен иметь понятную причину.

### P1: физическая геометрия и локализация недостаточно доказаны

`dicom_io._pixel_mm` берёт только первый компонент PixelSpacing и далее применяет один масштаб ко всем осям. Анизотропные пиксели не обрабатываются корректно. При отсутствии масштаба используется константа GE даже для неизвестного аппарата. Для исходного экспорта организатора оценка через ExposedArea может быть пригодной, но её нельзя автоматически переносить на любые DICOM. Нужны раздельные X/Y, явная область применимости fallback и тесты; для клинической доказательности — экспертные ориентиры и ошибка расстояний/углов на настоящих снимках. Синтетическая полоса с известным поворотом не подтверждает точность оси на реальной анатомии.

### P1: документация описывает разные версии решения

- Корневой README всё ещё говорит, что профильное обучение предстоит, хотя `competition/` содержит обученную модель.
- `APPROACH.md` сообщает один пропуск артефакта из 17; актуальный JSON — четыре. Для ротации бедра написано 18 пропусков, актуально 19.
- Заявление `<1 с на исследование` не соответствует сохранённому `full_batch_summary.json`: максимум 1.970 / 2.319 с. Лимит ТЗ 180 с при этом выполнен с большим запасом.
- Заявления о согласовании словаря, `quality_prob`, аппарата и исключения сколиоза встречаются в коде/README. В двух предоставленных PDF отдельного подтверждения этих уточнений нет; нужно включить исходные ответы куратора в комплект доказательств.

Перед сдачей нужен один маршрут запуска и один актуальный набор утверждений. Слайды должны показывать работающий конкурсный UI и настоящие результаты. Наличие демонстрационных пациентов в старом React не подтверждает возможности конкурсного сервиса.

## Что делать для борьбы за первое место

1. **Сначала надёжность сдачи:** собрать и запустить образ в чистом окружении, исправить найденные ошибки отчётности и кэша; проверить ZIP → API → CSV/XLSX → SC/SR без сети на инференсе. Зафиксировать release и контрольные суммы.
2. **Закрыть контракт:** подтвердить требования к ROI, проекции, мультифреймовым файлам, словарю, сколиозу, масштабу и набору аппаратов. Обновить матрицу соответствия по письменным ответам.
3. **Привести оценку к инференсу:** вложенная групповая CV для всего пайплайна и всех порогов; независимый контрольный набор, который не используется при выборе признаков. Это условие достоверного сравнения улучшений.
4. **Основную работу по модели направить на бедро:** экспертная перепроверка ошибок ротации, разметка ориентиров малого/большого вертела, шейки, диафиза и седалищной кости; сравнение геометрии с текущими эвристиками на одинаковых фолдах. Затем ось позвоночника и охват Th12. Больше данных полезно при совпадающих определениях меток и домене, а не просто за счёт размера внешнего датасета.
5. **Доказать объяснения:** экспертная ошибка угла, ошибка ключевых точек и отступов в миллиметрах; показать успешные и неуспешные случаи. Красивый overlay сам по себе не доказательство локализации нарушения.
6. **Подготовить защиту:** 8–10 слайдов: проблема, точные требования, данные/дубликаты, метод, честная валидация, сравнение моделей, ошибки, скорость/развёртывание, ограничения/пилот; демонстрация нормы, ротации, оси, артефакта, нескольких нарушений, повреждённого входа и пакетной обработки.

Не стоит сейчас расширять динамику, PACS-интеграцию и административные панели в ущерб качеству основной задачи. Они могут поддержать сценарий внедрения, но не компенсируют пропуски нарушений в закрытом тесте. Обоснованный следующий этап — инженерная приёмка и улучшение бедра с честным измерением прироста; целевые F1/AUC для победы из предоставленного ТЗ вывести нельзя.
