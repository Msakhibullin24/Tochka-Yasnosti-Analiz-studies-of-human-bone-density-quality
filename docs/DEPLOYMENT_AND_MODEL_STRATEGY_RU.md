# Модели, CI/CD и проверяемое развёртывание

Лучшая подтверждённая внутри проекта конфигурация остаётся прежней:
исследовательский GPU-классификатор 1.12.0, F1 0,619048, ROC-AUC 0,811877,
AP 0,693250, macro-F1 пяти типов 0,536340. Это ранее исследованная выборка
249 изображений / 100 исследований, условная на исторической маршрутизации;
независимость пациентов и максимальные возможные метрики не установлены.
Сборка, HTTP-проверка и успешный деплой не измеряют качество классификации.

## Как добиваться следующего улучшения

1. Сохранять сильный общий классификатор качества и изучать причины ошибок
   отдельно. Общий совет из семи источников и специализированный из восьми
   не превзошли текущую модель. Случайный рост F1 до 0,627 при падении AUC
   до 0,766 не принимается как улучшение всей системы.
2. Главная задача — сами измерения: физическая ось позвоночника имеет 8 пропусков
   из 10 размеченных нарушений; остаются приближённые границы Th12/вертела,
   мягкие ткани и разделение ротации. Голосование классификаторов не заменяет
   точные координаты и корректные определения признаков.
3. Новую анатомическую модель сначала проверять на отложенных донорах её
   собственного набора: ошибка координат, Dice областей, физическая устойчивость
   к масштабированию/повороту/отражению. Отдельно проверять перенос на DXA.
   Полная маска бедра не является истинной разметкой малого вертела; произвольный
   угол камеры не является клинической меткой правильной ротации.
4. До обучения фиксировать основную процедуру, метрику и критерий выбора.
   Все снимки одного исследования и известные дубликаты держать вместе.
   Подбор головы/порога/калибровки выполнять внутри внешнего обучающего разбиения;
   при обучении арбитра дополнительно получать внутренние OOF-прогнозы.
   Пять внешних / четыре внутренних разбиения не устраняют переобучение
   от многократного просмотра той же выборки.
5. Сравнивать кандидата с фактическим текущим GPU-incumbent, включая F1,
   AUC, AP, чувствительность, специфичность, пять типов и регионы, парные
   интервалы по исследованиям и калибровку вероятностей. Контрольный рост
   macro-F1 до 0,553 основан на одном исправленном пропуске ROI; его
   доверительный интервал включает отсутствие улучшения. Он не продвинут.
6. Только затем выполнять обучение финальных весов, экспорт без разметки,
   инференс из исходных DICOM, проверку отражения/маршрутизации, времени,
   повторяемости и восьми обязательных полей. Проверка на обучающем архиве
   подтверждает исполнение и отсутствие регрессии, но не новую точность.

## Запуск из готовой автономной поставки

Нужны Linux, Python 3 со стандартной библиотекой, работающий Docker и для
GPU совместимый драйвер NVIDIA. Сначала проверить контрольные суммы и загрузить
готовый архив образов из `delivery-1.12.0`. Он содержит все веса; скачивать
модели при запуске не требуется. Новый набор инструментов развёртывания
совместим и с этими ранее проверенными образами.

Из корня репозитория:

```sh
make deploy
make deploy-status
```

По умолчанию это GPU-образ `dxaqc:anatomy-fullfit-1.12.0-20261015`,
отдельная папка `data/deployment-gpu`, контейнер `dxaqc-managed-gpu`,
адрес `http://127.0.0.1:8093`. На текущей рабочей машине новый проверенный
управляемый GPU-сервис имеет имя `dxaqc-gpu-managed` и папку
`data/deploy-gpu-acceptance`; он не заменяет прежний сервис на 8091.
Чтобы управлять именно им, задавать эти `DEPLOY_NAME` и `DEPLOY_STATE`.

Без Make можно вызвать Python напрямую:

```sh
python3 competition/ops/deploy.py deploy \
  --mode gpu --image dxaqc:anatomy-fullfit-1.12.0-20261015 \
  --name dxaqc-managed-gpu --state data/deployment-gpu --port 8093
```

Отдельная установка CPU, с собственной папкой и портом:

```sh
make deploy DEPLOY_MODE=cpu DEPLOY_IMAGE=osseo-dxaqc:1.12.0 DEPLOY_PORT=8090
```

Смена CPU/GPU в существующей установке запрещена: это защищает от случайного
понижения качества при публикации CPU-образа. GPU не переключается на CPU
при отсутствии драйвера. Docker выбирается явно через `DOCKER_HOST`/`DOCKER_CONTEXT`
или используется стандартный движок; только при отсутствии явного выбора
скрипт умеет подключиться к уже существующему частному движку проекта.
Скрипт рассчитан на локальный Linux Docker, не на файловые тома удалённого daemon.

## Что проверяется до и после замены

- Образ уже установлен; его тег разрешается в конкретный image ID. Запуск
  использует этот ID, поэтому последующее изменение тега не меняет проверенный образ.
- Проверяются соответствие CPU/GPU, права владения контейнером, порт, устройства
  и драйверные библиотеки. Чужие контейнеры и занятые порты не перехватываются.
- GPU-набор сверяется с `competition/ops/approved_gpu_assets.json`: хеш самого
  manifest, все 31 файла весов/конфигураций, полный состав папки без лишних данных
  и 26 модулей инференса. Изменённые веса, код или незарегистрированные файлы
  блокируют выпуск до замены сервиса. Новая модель требует отдельного изменения
  политики с доказательствами метрик; успешный CI сам эту политику не меняет.
- Сначала запускается отдельный контейнер с отдельной SQLite и `--network none`.
  Изнутри него выполняется настоящий HTTP: readiness с ожидаемым профилем,
  интерфейс и assets, загрузка синтетического DICOM ZIP, ожидание задания,
  успешная обработка, CSV/XLSX, два дополнительных DICOM на успешный снимок,
  PNG, сохранность исходного ZIP и лимит времени исследования.
- Только после этого проверяется отсутствие активных заданий, останавливается
  прежний контейнер и сохраняется под отдельным именем. Перед новым запуском
  создаётся SQLite-backup. Модель и данные сохраняются отдельно.
- Новый сервис публикуется только на localhost и проходит тот же HTTP-прогон
  через опубликованный порт. При ошибке запускается прежний контейнер.
- У контейнера read-only root, временная `/tmp`, постоянный `/work`, ограниченные
  Docker-логи, healthcheck и `restart: unless-stopped`. API использует обычную
  Docker-сеть, необходимую для rootless-публикации порта; изоляция `network none`
  относится к предварительной проверке и пакетному режиму, не к опубликованному API.

Профили CPU и GPU различаются. Для текущих образов выбираются соответственно
`tz-delivery-1.12.0` и `research-live-anatomy-qc-20261015`. Если готовый сервис
сообщает другой профиль, проверка немедленно завершается ошибкой.

Обновление имеет короткое окно обслуживания. Перед ним следует приостановить
загрузки: проверка отсутствия активных заданий сама по себе не блокирует новые
HTTP-запросы. Нулевой простой и откат произвольных несовместимых миграций SQLite
не обещаются. Сохранённый backup предназначен для отдельного восстановления
данных; автоматический откат возвращает контейнер и сохраняет рабочую папку.

## Откат и наблюдение

```sh
make deploy-rollback
make deploy-watch
```

Команды принимают те же `DEPLOY_NAME` и `DEPLOY_STATE`, что использовались при
установке. В `STATE/runs/RUN_ID/` находятся протокол, хеши экспортов и журналы;
`current.json` записывается атомарно только после успешной проверки.
Операции изменения сериализованы файловой блокировкой.

Docker restart policy восстанавливает завершившийся процесс, но сама по себе
не перезапускает живой `unhealthy` контейнер. Поэтому `watch` отдельно проверяет
готовность и перезапускает только свой работающий контейнер, если Docker уже
подтвердил `unhealthy`. Состояние `starting` и намеренная остановка не вызывают
перезапуска. Повторные неудачи должны попадать во внешнее оповещение администратора.
[Поведение restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/).

Для обычного серверного Docker приложены `competition/ops/dxaqc-watch.service`
и `.timer`. Их установка на сервере требует существующей служебной учётной
записи с доступом к Docker и файла `/etc/dxaqc/deployment.env`:

```ini
DXAQC_CHECKOUT=/opt/dxaqc
DXAQC_DEPLOY_STATE=/srv/dxaqc
DXAQC_DEPLOY_NAME=dxaqc-production
```

Настроить пользователя service unit на учётную запись развёртывания, скопировать
units в каталог systemd и включить timer. Движок Docker также должен стартовать
при загрузке ОС. На текущей машине системные units не установлены; проверен
сам watchdog. Перезагрузка всего хоста отдельно не проверялась.

## CI и публикация

`.github/workflows/ci.yml` запускает:

1. Actionlint фиксированной версии с проверкой SHA-256.
2. Проверки интерфейса и production-сборку с lockfile.
3. Backend-тесты из `uv.lock`.
4. Сборку CPU-образа, контейнерные тесты и CLI-проверку ZIP.
5. Тесты неудачного обновления/владения/отката/watchdog и реальное развёртывание
   с изолированным и опубликованным HTTP-прогонами. JSON-доказательства сохраняются
   в Actions artifacts, включая неудачные прогоны.

Фронтенд-тесты ищутся только в `src/`: локальные копии Docker-слоёв и датасеты
не должны участвовать в тестовой коллекции.

Публикация CPU: `release.yml`, GPU: `gpu-release.yml`. Они запускаются вручную
только из `main`, после того же полного CI. Публикуется проверенный образ с тегом
коммита; деплой использует возвращённый registry digest, а не изменяемый `latest`.
Для GHCR применяется `GITHUB_TOKEN` с минимальными правами.
[Официальная схема GitHub](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images).

CPU-deploy требует частного runner с меткой `dxaqc-deploy`, environment `production`,
`DXAQC_DEPLOY_ENABLED=true`, `DXAQC_DEPLOY_STATE` и при необходимости
`DXAQC_DEPLOY_PORT`. GPU-release требует частного GPU-runner с меткой `dxaqc-gpu`,
environment `gpu-release`, переменных `DXAQC_ANATOMY_ASSETS` (абсолютный путь
к подготовленным model-only assets), `DXAQC_ANATOMY_ENV_IMAGE` (установленный
проверенный образ среды), `DXAQC_GPU_RELEASE_STATE`, а для деплоя
`DXAQC_GPU_DEPLOY_STATE` и необязательного `DXAQC_GPU_DEPLOY_PORT`.
Исходные обучающие изображения не нужны для GPU-сборки.
Пути моделей и постоянного состояния должны быть абсолютными и находиться
**вне `GITHUB_WORKSPACE`**, например под `/srv/dxaqc/`: checkout очищает рабочую
копию. Проверка этих путей выполняется до checkout, чтобы защитить данные.

Публичные PR не запускаются на частных GPU/deploy-runner. Обновление моделей
не происходит автоматически от успешного CI: результаты метрик и экспорт весов
проверяются отдельным исследовательским процессом, описанным выше.
GitHub Actions, GHCR и удалённый сервер требуют настроенных runner/прав аккаунта.
В этой сессии нет авторизованного GitHub CLI; удалённые release/deploy workflows
не запускались. Локальные контейнерные проверки выполнены реально.

[Машинный протокол локальной проверки](competition/deployment_acceptance_2026_10_15.json)
содержит image ID, результаты установки/обновления/откатов и границы проверки.
