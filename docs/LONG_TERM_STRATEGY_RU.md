# Долгосрочное развитие Osseo AI

Дата: 20.09.2026. Горизонт: месяц до финала, затем 3–6 месяцев развития. Эксперта пока нет. PACS исключён из текущего плана. Это стратегия и критерии принятия решений, а не перечень уже реализованных функций; текущее состояние — в `IMPLEMENTATION_STATUS_RU.md`.

## Главный результат

Продукт должен помогать специалисту завершать контроль исследования и при этом накапливать проверяемые данные для следующих улучшений. Устойчивое преимущество может появиться из сочетания точной модели, проверяемых объяснений, удобной проверки и воспроизводимых выпусков. Само наличие редактора или большой сети такого преимущества не доказывает.

Состояние 1.1.0: исправлен основной технический контур, реализованы экспертные версии, есть Docker и проверки. Прироста точности пока нет: AUC 0.793, F1 0.583; macro-F1 итоговых типов — 0.461 для позвоночника и 0.506 для бедра. Эти числа определяют приоритеты: улучшать типы нарушений и качество основной модели важнее, чем добавлять самостоятельные новые разделы.

## 1. Сделать воспроизводимым весь путь результата

Целевая цепочка: исходный объект → нормализованное изображение и преобразования → запуск конкретной модели → машинное решение → экспертная версия → принятая версия разметки → кандидат модели → независимая оценка → выпуск.

Нужны разные идентификаторы и правила для разных сущностей:

- **Исходный файл:** хеш оригинальных байтов, исходные DICOM UID, параметры чтения. Повторная загрузка файла не создаёт неразличимую копию.
- **Изображение для анализа:** хеш пикселей, размер, физический масштаб, ориентация и преобразования. Это ключ вычислительного кэша, а не универсальная идентичность исследования.
- **Запуск:** ссылки на вход, хеши весов и кода, настройки, версия правил, время и результат. Новый анализ создаёт новый запуск.
- **Экспертная версия:** ссылка на конкретный запуск/изображение, автор, причина, геометрия и номер версии. Она не переписывает историю модели.
- **Версия обучающих данных:** список принятых чтений, происхождение и правила исключения, идентификаторы групп, зафиксированные разбиения.

Сейчас `row_id` зависит от пути внутри пакета, а сведения о модели не образуют полного паспорта запуска. Для локального пакета этого достаточно, но при повторных загрузках и переобучении нужны устойчивые связи между объектами. Физически одинаковые пиксели с разными метаданными нельзя безусловно считать одним исходным DICOM.

Решение о хранении оригиналов принять явно: управляемое локальное хранение с лимитом/сроком либо ссылка на внешний неизменяемый архив с проверкой хеша. Сохранять только preview недостаточно для воспроизведения декодирования DICOM и проверки новой предобработки. Нельзя одновременно обещать удаление оригиналов после загрузки и полный повтор анализа без исходных данных.

## 2. Разделить рабочие правки и эталонные метки

Нажатие «Подтвердить» в интерфейсе означает сохранённое решение пользователя, но не автоматически независимый эталон для обучения. Пользователь мог видеть подсказку модели; проверяться чаще могут сложные и подозрительные случаи. Обучающий поток должен сохранять эти обстоятельства.

Предлагаемый процесс:

1. Рабочая проверка создаёт кандидатную разметку с происхождением, видимостью подсказки ИИ и причиной изменения.
2. Отдельный протокол определяет, какая разметка может попасть в обучение, какая требует повторного чтения, какая остаётся неопределённой.
3. Исходные метки организатора сохраняются; изменения создают новую версию, а не заменяют конкурсный эталон задним числом.
4. Контрольная выборка исключена из подбора признаков, порогов и обучения. Её нельзя автоматически пополнять случаями, уже использованными для разработки.
5. Для оценки рабочего качества нужна также случайная выборка потока, а не только очередь ошибок и неуверенных ответов модели.

Без эксперта можно подготовить инструмент, очередь расхождений, инструкции и версии данных. Нельзя создавать «подтверждённые» анатомические метки самостоятельно или подгонять эталон под предсказание.

## 3. Исследовать модель ограниченными сериями экспериментов

До финала оставаться в текущей задаче: позвоночник/бедро и согласованные типы нарушений. Провести небольшую заранее описанную серию экспериментов:

| Гипотеза | Что сравнить | Условие принятия |
|---|---|---|
| Геометрия бедра недостаточно устойчива | Текущие измерения и локальные изменения выделения контура/оси | Сопоставимый протокол, показатели бедра и типов, отсутствие неприемлемых регрессий |
| Бинарный класс подавляет полезные типы | Текущая композиция и альтернативное согласование общего класса с типами | Оценка реально выдаваемого CSV; правила выбора зафиксированы до сравнения |
| Порог и score плохо переносятся между разбиениями | Внутренняя настройка порогов, кандидат с калибровкой и без неё | F1 по повторам, чувствительность/специфичность, проверка калибровки; прирост AUC не предполагается |
| Предобработка хрупкая | Парные тесты яркости, умеренного шума, поддерживаемых форматов и физического масштаба | Для преобразований, сохраняющих смысл, измеренная стабильность; для реального изменения укладки — ожидаемое изменение ответа |
| Ошибки роутера и полярности скрыты раздельной оценкой | Сквозной held-out прогон от DICOM до официальных меток | Отдельная публикация качества полного контура и его компонентов |

Гипотезы — не обещания улучшения. Результат «не помогло» сохраняется, чтобы не повторять перебор. Рабочая модель заменяется только после согласованного сравнения и проверки совместимости.

На следующем этапе экспертные ориентиры позволят сравнить эвристики с обучаемым локализатором. До получения таких данных не выбирать большую архитектуру как готовый ответ на проблему ротации. Не смешивать внешние изображения с другой подачей/таксономией только ради числа файлов.

## 4. Оценивать полезность объяснений и интерфейса

Для каждого типа нарушения сформировать карточку: что оценено, где основание на снимке, что измерено, насколько измерение доступно, какой источник масштаба и какое действие выполняет специалист. Прямое измерение, косвенный признак и итоговая гипотеза должны различаться.

Порядок доработки UI:

- просмотр исходника и наложений рядом либо быстрым переключением;
- понятные названия ориентиров, единицы и недоступные измерения;
- перемещение точек мышью при сохранении точного ввода и клавиатурного управления;
- переход к следующему изображению, сохранённая позиция очереди, видимый статус проверки;
- сравнение машинной разметки и конкретной экспертной версии;
- история по исследованиям с несколькими изображениями, а не только по загруженным пакетам.

Измерять время завершения стандартного сценария, число лишних действий, успешность сохранения/возврата к работе, частоту конфликтов и потерянных правок. Для проверки понятности интерфейса можно привлекать пользователей без клинической экспертизы; это не подтверждает правильность медицинского результата.

При появлении специалиста отдельно проверять правильность ориентиров/углов/отступов и полезность объяснений. Полностью успешная выгрузка 499 DICOM проверяет инженерную надёжность, но не эти свойства.

## 5. Развивать архитектуру по измеренной потребности

Сохранить модульный монолит, один API, один основной UI и локальную SQLite. Текущий объём данных не даёт оснований немедленно переходить на распределённые сервисы. Рабочие границы: чтение и нормализация, признаки/модель, правила решения, задания/хранение, экспертные версии, экспорт, UI.

Ближайшие долговременные улучшения:

- Инициализация схемы при старте и явные миграции вместо повторного DDL при каждом получении Store.
- Разрешённые переходы состояния задания и смена состояния с проверкой ожидаемого предыдущего значения.
- Идемпотентная загрузка и отчёт о повторе; повтор вычислений не должен удваивать экспертные записи.
- Ссылки на артефакты относительно корня хранилища, чтобы перенос не зависел от абсолютных путей контейнера/хоста.
- Чекпоинты по изображениям и продолжение после сбоя при наличии сохранённого входа; прерванный экспорт не публикуется как готовый.
- Явное наблюдение за worker: если он остановился, readiness отражает это, а очередь не остаётся навсегда «работающей».
- Лимиты очереди/диска и управляемое удаление связанных артефактов без осиротевших записей.
- Закреплённые контракты API и отдельные компоненты клиента, редактора и экспертного сохранения по мере роста UI.

Старый исследовательский контур должен иметь ограниченное назначение и понятные условия переноса нужных инструментов/удаления устаревших частей. Не развивать две независимые реализации одной и той же проверки качества.

Переход на серверную СУБД или несколько workers оправдывается измеренной конкуренцией, размером очереди и требованиями нескольких рабочих мест. Перед таким переходом нужны аутентифицированные роли и модель владения заданиями; введённое имя эксперта нельзя считать удостоверением личности.

## 6. Выпуск модели и выпуск приложения — разные события

Каждый выпуск приложения должен иметь идентифицируемую ревизию исходников, контейнер, хеши зависимостей/весов, совместимость схемы БД и отчёт проверок. Приложение может обновиться без замены весов — как в 1.1.0.

Каждый кандидат модели проходит отдельно: зафиксированная версия данных → обучение → оценка → решение о принятии → пакет модели → переключение → возможность отката. Откат весов не должен уничтожать новые экспертные версии или требовать отката базы данных.

Минимальный набор защитных проверок: DICOM→CSV для обеих областей; ошибки/отмена/перезапуск; повторная загрузка; неизменность машинного результата после правок; конфликт версий; backup→restore в другой каталог; интерфейс в настоящем браузере; тест публичного скрипта с ZIP; отсутствие сети на инференсе. Учитывать время и память по стадиям, а также отдельно время очереди и анализа.

Сейчас значительный набор изменений находится в рабочем дереве. До следующей большой серии изменений следует зафиксировать проверенную базовую ревизию и связать с ней выпуск; иначе сравнение последующих результатов будет затруднено.

## Приоритеты по горизонтам

| Горизонт | Основной результат | Условие перехода |
|---|---|---|
| До финала, около месяца | Законченный основной сценарий, честные эксперименты, воспроизводимая сдача | Фиксированная версия, сквозные проверки, отчёты качества, отрепетированная демонстрация |
| Следующие 1–3 месяца | Полное происхождение данных, управляемые версии, пилотная экспертная разметка при появлении партнёра | Воспроизводимый повтор исходного расчёта и независимая оценка хотя бы одного улучшения |
| 3–6 месяцев | Ограниченный пилот на определённом аппарате/формате и доказанная полезность рабочего процесса | Измеренные результаты на новом потоке, подтверждённые ограничения, понятная стоимость сопровождения |

Если эксперт и новые данные не появляются, сместить работу на воспроизводимость, удобство, протоколы и техническую устойчивость. Не выдавать этот прогресс за клиническую валидацию.

## Три следующих пакета работ

1. **Воспроизводимость:** стабильная идентичность входа, паспорт запуска, правила хранения оригиналов, контрольный набор и базовая ревизия. Приёмка — повторить результат после переноса среды с теми же входом/версией модели.
2. **Качество:** сквозная оценка с роутером и заранее выбранные эксперименты по бедру/типам. Приёмка — парное сравнение и объяснение ошибок; отсутствие прироста тоже допустимый результат исследования.
3. **Работа специалиста:** удобный редактор и очередь, происхождение каждой правки, подготовка данных к независимому чтению. Приёмка — законченный сценарий без потери информации и без автоматического превращения правок в эталон.

Приоритет каждого нового предложения проверять тремя вопросами: какую наблюдаемую проблему оно решает, как измерить улучшение, что придётся поддерживать после добавления. Если ответов нет, держать предложение в списке гипотез, а не включать в основной продукт.
