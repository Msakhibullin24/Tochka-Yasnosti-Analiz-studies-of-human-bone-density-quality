## 1. Как пользоваться тремя планами

1. **Этот документ** — главный список закрытия требований, новые эксперименты и порядок приёмки.
2. [Runbook метрик](METRIC_UPGRADE_AGENT_RUNBOOK_2026_10_09_RU.md) — baseline, данные и команды существующих исследовательских инструментов.
3. [Консорциум/VLM](MODEL_CONSORTIUM_VLM_RESEARCH_2026_10_09_RU.md) — кандидаты MedGemma/Qwen, локальный vLLM, роли моделей и эксперименты по арбитру.

Использовать все полезные классы подходов: CV, анатомию, геометрию, VLM, текстовый LLM, OCR и экспертные данные. Каждому компоненту нужна конкретная проверяемая задача. Все найденные веса не должны автоматически становиться участниками итогового решения: сравнивать кандидатов, сохранять отрицательные результаты, включать измеренно полезные компоненты.

## 2. Что прямо требует ТЗ

- §2.2: область и проекция, QC, укладка, корректность разметки, несколько нарушений, структурированный отчёт.
- §2.3: позвоночник — половина Th12, верхние края подвздошных костей, ось до 5°, посторонние предметы; бедро — большой вертел, шейка, седалищная кость, ротация по малому вертелу и отступы 30/30/20 мм.
- §2.4: DICOM без разметки, до трёх изображений/серий в исследовании, отсутствие зависимости от персональных данных.
- §2.5 и V2: одна строка на изображение, CSV/XLSX, фиксированные названия областей и нарушений, `quality_prob` в [0,1], несколько типов через `;`.
- §2.7: не более 180 секунд на исследование, обработанные ошибки и повторяемость.
- §3.2: контейнер, Unix-скрипт, локальный офлайн-запуск, API пакетной обработки, закреплённые зависимости.
- §4–5 и §7.2: документация, презентация, все веса, воспроизводимое обучение/запуск и готовая финальная поставка.
- §8.4: метрики отдельно по областям, F1, ROC/PR-AUC, macro-F1 типов, локализация при её реализации и доверительные интервалы. В перечне нет обязательного численного F1=0,9.

§2.6 прямо называет визуализации, SR, коррекцию разметки и веб-интерфейс **дополнительными** функциями. Для полного заявленного продукта их тоже проверить, но не смешивать с обязательными требованиями. PACS, прогноз BMD по изображению и клиническая интерпретация динамики не добавлять как новые обязательные пункты конкурса.

ТЗ описывает **две H200 141 GB в отдельных ВМ**, каждая с 44 CPU / 256 GB RAM / 141 GB VRAM. Без подтверждённой межмашинной конфигурации не считать это одним устройством с 282 GB VRAM и не рассчитывать на `tensor_parallel_size=2` внутри одной ВМ.

Новый patient-disjoint тест R16 и стресс-сценарии R15 — выбранные способы усиления доказательности и проверки требований. Конкретный размер такого теста, отдельная клиническая сертификация и обязательная поддержка восьми параллельных запросов в ТЗ не заданы.

### Блокер ROI требует отдельного решения

§2.4 описывает вход без разметки, §2.2 требует оценить её корректность. V2 не определяет контейнер исходной операторской разметки. Получить разъяснение: проверяется геометрия охвата на снимке, отдельная операторская ROI или обе задачи, и откуда приходит ROI.

Можно подготовить поддерживаемый локальный контракт и примеры входа сейчас. Если оригинальная ROI не существует во входе, LLM/VLM не сможет доказать её исходную корректность. Автоматически предложенный контур — результат коррекции/предложения, отдельный от оценки исходной разметки. Без согласованного определения и эталона этот пункт не объявлять закрытым.

## 4. Конкретные роли LLM, VLM, OCR и vLLM

### VLM по изображению

Использовать MedGemma 1.5 4B и Qwen3.5-9B как два сравниваемых кандидата по протоколу предыдущего документа. Давать полный кадр, а дополнительный crop — отдельной абляцией. Проверять видимость структуры, подозрение на артефакт, укладку и причины unknown. Ответ сохранять с моделью, revision, prompt hash и координатным преобразованием.

Первоначально VLM работает в режиме наблюдения. Влияние на официальный QC добавлять только после проверки дополнительной информации на новых данных. Не вводить отдельный голос за каждый промпт одного и того же энкодера.

### LLM с локальным поиском по ТЗ

Создать небольшой локальный индекс из ТЗ, V2 и нужных разделов методических рекомендаций. Для этих документов сначала сравнить обычный поиск по разделам с embedding retrieval; большой RAG-фреймворк необязателен.

LLM получает **готовые измерения и criterion states**, извлечённый фрагмент правила и ссылки на доказательства. Он составляет понятное объяснение, проверяет наличие обязательных полей и предлагает экспертную очередь. Источник каждого правила включает документ, раздел, страницу и версию.

Нормативные сравнения 5° и 30/30/20 мм выполняет код. Официальные названия типов выбираются из словаря V2. LLM не создаёт новые медицинские правила и не перезаписывает class/probability. Сохранить template baseline для сравнения качества текста и неподтверждённых утверждений.

### OCR/VLM для подписей и ROI-экспорта

Новый кандидат: [PaddleOCR-VL-1.5](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.5); карточка также указывает [1.6](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6). Это модели разбора документов, не модели QC костей. Предлагаемая роль: извлечение надписей уровня, единиц и табличных полей из отчётного экспорта. Выбрать одну версию после собственного теста; не обещать преимущество 1.6 на DXA.

Разделить задачи: OCR читает подпись, CV восстанавливает геометрию линии/контура. OCR сам по себе не выдаёт ROI-полигон и не доказывает правильную нумерацию позвонка. Если разметка «впаяна» в пиксели, сохранять это происхождение и проверять точность восстановления; не обозначать результат как извлечение структурированного DICOM Overlay.

Структурированные ROI имеют приоритет перед OCR. Сверить импорт с первичными разделами DICOM: [Graphic Annotation](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.10.5.html) и [Overlay Plane](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.9.2.html).

### vLLM для исполнения

Использовать отдельное окружение/контейнер VLM и локальный API. [Structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/) ограничивают форму ответа, но не устанавливают истинность наблюдений. Сначала один запрос/модель, короткий фиксированный ответ; затем измерить batching и очередь.

Не включать web search для каждого DICOM: официальный маршрут должен работать без внешней сети. Интернет нужен для подготовки моделей/данных, после чего файлы и версии фиксируются локально.

## 6. Ещё 20 проверяемых экспериментов для метрик

Каждую гипотезу сравнивать с заранее выбранным baseline на одних фолдах. На независимом test не перебирать параметры. Указанные методы не объявляются новыми для всей науки или гарантированно полезными; часть похожих вариантов уже исследовалась в проекте.

| № | Эксперимент | Конкретный дизайн и условие продолжения |
|---|---|---|
| E01 | Проверка разметки и конфликтов | Повторная независимая разметка всех FN и выборки TN/FP; сохранить версии, оценить согласие |
| E02 | Отдельная проекция/сторона | Небольшой router с unknown-выходом; сравнить полный QC с oracle-region только как диагностикой |
| E03 | Полный кадр + анатомический crop | Две ветки с общей принадлежностью пациента; проверить, улучшился ли дефект без потери охвата |
| E04 | Более точная предобработка | Сравнить 8-bit baseline с представлением большей динамической точности при наличии источника; учесть polarity/VOI, не выдумывать 16-bit из 8-bit |
| E05 | Анатомия в физической сетке | Сохранить обратимое отображение X/Y; проверить ошибку угла и расстояний после resize/mirror |
| E06 | Анатомические constraints | Порядок L1–L4 и правдоподобие точек с abstention; не дорисовывать невидимые структуры |
| E07 | Локальная голова артефактов | Bbox/mask labels предметов + hard negatives ROI-линий, нормальных костей, имплантатов |
| E08 | Голова подтипов ротации | Normal/under/over/unknown, контур малого вертела; официальная метка по прежнему словарю |
| E09 | Multi-task learning | Общий энкодер + masks/keypoints/visibility/QC; маски неизвестных targets, отдельные ablations loss |
| E10 | Partial-label training | Loss только по известным критериям; различать отсутствие метки и отрицательный ответ |
| E11 | Дисбаланс | Сравнить weighted BCE и одну заранее выбранную focal/ASL конфигурацию; не выбирать по test |
| E12 | Сложные отрицательные | Добавить ошибочные тревоги train, рамки и нормальную нетипичную анатомию; исключить выбор тестовых строк |
| E13 | Domain-adaptive SSL | Chinese DXA train-only, затем supervised probe; сравнить с исходным frozen backbone |
| E14 | Метки из синтетики | Crop для охвата, реальные масштабы, артефакты как вспомогательные данные; child в fold родителя |
| E15 | Train-only псевдометки | VLM/teacher предлагает, эксперт проверяет контроль; не использовать их как gold-test |
| E16 | Калибровка по критериям | Temperature/Platt baseline; сложную isotonic только при достаточных данных; Brier и reliability plots |
| E17 | Арбитр доказательств | Простое среднее против регуляризованного stacking; общие FN, error correlation, вложенное обучение |
| E18 | TTA/ensemble масок | Одиночный FleXray против ансамбля; вернуть каждое преобразование в исходную систему, замерить цену времени |
| E19 | Дистилляция | Сохранить лучшие учительские признаки в компактном student; проверить студента без учителя |
| E20 | Сдвиг аппарата/потока | Held-out vendor/center/time; измерить калибровку и метрики при иной частоте дефектов |

2D поворот кадра не создаёт реальную внутреннюю/наружную ротацию бедра. Дорогую 3D/DRR-синтетику рассматривать после baseline на реальных данных; синтетическая геометрия не заменяет реальные положительные случаи и независимый тест.

Для ROI вместо IoU всего прямоугольника проверить содержательные свойства: принадлежность шейки, исключение большого вертела, ориентацию к оси шейки, мягкую ткань по сторонам и правильность назначенных уровней. Конкретные правила сверить с методическими рекомендациями, не формировать их из ответа VLM.

Сравнение ≥2 кадров одного исследования может дать контекст, но не должно подменять оценку конкретного изображения соседним. Если один кадр показывает Th12, это не доказывает его видимость на другом. Все связанные кадры остаются в одном split.

## 7. Данные и экспертный консорциум

Практический начальный бюджет:

- 200 новых изображений — пилот labelbook и формата точек/масок.
- 1000–3000 исследований — следующая гипотеза размера обучающего корпуса, уточняемая по learning curve.
- Целенаправленный набор реальных редких дефектов; 100 позитивов на критерий — начальный ориентир, не гарантия узкого интервала.
- 2–3 центра с разными аппаратами, контрольная часть размечается двумя экспертами, разногласия разрешаются отдельно.
- Отдельный последовательный поток обычной частоты и отдельный сложный стресс-набор.

Chinese DXA — кандидат масштабирования, Ramathibodi — небольшой проверенный внешний источник. UK Biobank — путь с контролируемым доступом, не немедленная загрузка и не обещанный набор наших QC-меток. Список источников и условия см. в прежних планах.

Роли: координатор данных/меток, специалист по DXA, разработчик анатомии/геометрии, разработчик QC/VLM, ответственный за evaluator/релиз. Это распределение ответственности; участники и клиники ещё не привлечены. Если нет возможности обмена данными, сначала общий evaluator и локальное тестирование фиксированной модели, затем пилот FLARE.

Разметка должна включать идентичность исследования, область/сторону/проекцию, видимость/обрезку, точки/маски, операторскую ROI с происхождением, все применимые нарушения и неизвестные ответы. Персональные поля не должны становиться входом модели; ключи для группировки хранить отдельно от её признаков.

## 8. Что изменить в коде, чтобы закрытие было реальным

В `competition/dxaqc/requirements.py` проверки `vertebral_numbering_and_roi`, `scan_coverage`, `rotation` сейчас явно формируют `undetermined`. Проекция зависит от `clinical_validation`, ориентиры — от `verified`. Наличие новой модели не снимает эти блокеры автоматически.

Предлагаемая работа:

1. Ввести единый результат критерия: статус pass/fail/undetermined/not_applicable, основание, измерение/единица, пригодность, source UID и координатное пространство.
2. Хранить отдельно регистрацию проверенной версии модели: хеш, область применимости, definition version, ссылка на eval-report и заранее определённые критерии допуска. Не делать общий переключатель `clinical_validation=true` заменой этой информации.
3. Обновлять `image_checks()` по подтверждённым измерениям и применимости; различать «модель технически исполнилась» и «критерий проверен».
4. Для каждого обязательного критерия требовать проверяемое основание. Missing ROI не должен исчезать из полноты через удобный `not_applicable`, пока исходный контракт не определён.
5. Статус полной приёмки считать по результатам всего маршрута и доказательствам; не менять флаг ради зелёного отчёта.
6. Проверить согласие criterion states, общего класса, типов, объяснений и экспортов. Калиброванный общий риск не обязан численно равняться noisy-OR при зависимых критериях, но не должен противоречить подтверждённому правилу решения.

Рекомендуемые изменения по границам:

| Граница | Что реализовать |
|---|---|
| `gpu_research/`, `experiments/` | Данные, обучение, prompt evaluation, вложенный арбитр, сохранение результатов |
| `dxaqc/source_roi.py` | Поддержка согласованных источников и корректное происхождение координат |
| `dxaqc/geometry.py`, анатомические модули | Пригодность ориентиров, физические измерения, видимость и погрешность |
| `dxaqc/pipeline.py`, `decision.py` | Новый проверенный профиль маршрута без обхода официальных порогов |
| `dxaqc/requirements.py` | Полнота, применимость и ссылки на реальные доказательства |
| `dxaqc/api.py`, отчёты | Единый Failure и единая формулировка положительного ответа без типа |
| Версионные модели/паспорт | Закреплённый комплект и откат всего профиля |

Новые имена схем/полей — проект изменений, не заявление об уже существующем API. Официальные CSV и сохранённые экспертные версии сохранить совместимыми.

## 9. Дополнительный функционал и обнаруженные продуктовые проблемы

- Проверить SC/SR: source references, UID, геометрию и внешний DICOM conformance. Читаемость через pydicom сама по себе недостаточна. Причины дефектов исходных UID учитывать отдельно.
- В коррекции ROI хранить исходную, машинно предложенную и подтверждённую экспертную версии отдельно; преобразования координат и авторство должны воспроизводиться.
- Устранить формулировку «Нарушений не выявлено» для положительного ответа без типа в карточке исследования, если проблема ещё воспроизводится.
- Для `/compare` привести внутренний сбой модели к структурированному Failure, если прежняя проблема не исправлена.
- Для динамики МПК отделить сходство укладки от разрешения интерпретации изменения; не использовать неопределённое QC и неподтверждённый LSC как основание значимости. Это качество уже заявленного продукта, не новый пункт конкурса.
- Унифицировать независимый манифест всех поддерживаемых входных файлов; старый `audit_delivery.py` собирает только `.dcm`. Для GSPS явно описать, какие входные объекты являются аннотациями, а не отдельными анализируемыми изображениями.

## 10. Приёмка качества, времени и поставки

### Статистическая приёмка

Заранее выбрать главную цель: F1/AUC конкурса плюс macro-F1 и ограничения на чувствительность/специфичность. Для продукта дополнительно риск ошибочного автоматического допуска и coverage. Не требовать механического роста всех чисел любой ценой; заранее определить допустимые компромиссы и проверки отдельных требований.

Полный отчёт содержит split/manifest, все параметры поиска, каждый seed, результаты по областям/критериям, FN/FP, отказ/unknown, uncertainty и групповые интервалы. Нельзя называть интервалы пациентскими, если доступен только study key. Хранить долю случаев, где метрика неопределена из-за отсутствия позитивов.

Оценка нового энкодера с истинной областью и сохранённой осью — диагностический эксперимент, не полноценная приёмка нового pipeline. Финальная оценка проходит от сырого DICOM до экспорта.

### Техническая приёмка

1. Замер на **одной** целевой ВМ H200: полное исследование до трёх кадров, загрузка/предобработка/модели/арбитр/экспорт.
2. Проверка cold/warm start, худшего поддерживаемого входа, очереди, отмены, повреждённых данных и диска.
3. Укладываться в 180 секунд по принятому определению времени; до уточнения публиковать отдельно чистый инференс, полное время и ожидание очереди.
4. Один GPU-scheduler/ограничитель одновременно используемой памяти для batch/analyze/compare. Не разрешать каждому VLM-server резервировать 80% одного GPU одновременно.
5. Cache по пикселям+предобработке+весам; повторно использовать энкодер для совместимых голов. Исключить stale cache.
6. Сравнить ONNX/компиляцию/квантизацию выбранной модели, а не оптимизировать весь зоопарк. После оптимизации повторить медицинские сравнения.
7. Офлайн-тест без сети со всеми локальными весами/процессорами/RAG-индексом; никакого скачивания при старте.
8. Повторные ответы сравнивать по медицинским полям. `temperature=0` не считать доказательством побитовой GPU-детерминированности; проверить фактическую устойчивость статусов и вероятностей.

### Исполняемые проверки уже существующего проекта

```bash
make verify
./competition/run.sh build
./competition/run.sh test
./competition/run.sh batch /absolute/input.zip /absolute/new-output complete
```

Режим `complete` сейчас может вернуть код 3 при незакрытой анатомии; отчёт сохранится. Это блокер, который надо устранить доказанной реализацией, а не отключением проверки.

```bash
PYTHONPATH=competition competition/.venv/bin/python competition/audit_delivery.py \
  --input /absolute/extracted-dicom-folder \
  --results /absolute/new-output \
  --output /absolute/new-audit.json
```

Эта команда существует для `.dcm`-набора; не выдавать её нынешний манифест за проверку всех произвольных DICOM-расширений. Команды новых моделей находятся в двух предыдущих документах. Новый evaluator, OCR-адаптер и registry ещё требуется реализовать.

## 11. Порядок работы и контрольные точки

| Этап | Что выполнить | Когда переходить дальше |
|---|---|---|
| A | Инвентаризация ТЗ/данных/весов, baseline, split и договорённость ROI | Нет неявных определений и утечки, блокеры записаны |
| B | Экспертный пилот, ось, редкие критерии, маски и исходные ROI | Есть проверенный labelbook и пригодные targets |
| C | Router, анатомия, visibility, нумерация и физическая геометрия | Для R02–R10 есть самостоятельные измеренные проверки |
| D | Multi-label QC, MedGemma/Qwen/OCR-пилот, текстовый LLM | Для каждого компонента известен эффект и цена ошибок |
| E | Арбитр/калибровка, дистилляция, фиксированный кандидат | Конфигурация выбрана без доступа к независимому test |
| F | Новый test, H200, Failure/offline/repeatability | По всем обязательным строкам матрицы есть доказательства |
| G | Новый профиль, документация, демо и проверенный откат | Другой разработчик воспроизводит результат; поставка готова к оценке организатора |

Сроки зависят прежде всего от реальных экспертных данных и доступа к аппаратам; не обещать «все ТЗ за N дней» по одному скачиванию моделей.
