# Сквозной конвейер, профиль запуска и состояние ТЗ

Текущий профиль кода: `data/specialists/runs/no-new-labels-runtime-v5-20260926/profile.json`. Он использует прежние веса v2 и исправленный конвейер обработки. Новые врачебные метки не создавались. Кандидат обучения на полярностях v3 отклонён; его результаты не включены в поставочный профиль.

Версия базовой модели остаётся 1.10.0. Идентичность текущего кода и дополнительных моделей определяется **workflow_profile_id**, SHA-256 профиля и digest контейнера. Старые отчёты v1/v2 относятся к прежнему коду: запускать их следует в соответствующем старом образе. Их локальные команды с текущим деревом исходников должны отклоняться проверкой контрольных сумм.

## Исправления

1. Ранее сравнение ROI использовало выпуклую оболочку кандидата и теряло отверстия и вогнутые участки маски. Теперь в `learned_anatomy.py` сохраняется точная маска крупнейшей связной компоненты: отверстия и вогнутые участки не заполняются. Полигон остаётся отдельным предложением ROI; для старых полигонных результатов происхождение обозначено как выпуклая оболочка.
2. `mask_raster.py` задаёт единое представление масок и для предсказаний, и для DICOM overlays. Размеры, целочисленные координаты, границы и непересечение runs проверяются до выделения массива; предельные размеры и количество runs ограничены.
3. Проверка яркости бедра сравнивает одну и ту же эвристику до и после изменения яркости. Разница между нейросетью и эвристикой больше не выдаётся за нестабильность. Общий результат имеет область действия `heuristic_geometry_only`; устойчивость заменённого нейросетевого центра шейки обозначена как непроверенная.
4. Отчёт показывает доступные кандидаты L1–L4 и отсутствующие уровни. Он не объявляет их подтверждённой нумерацией и не сообщает об их отсутствии, если модель вернула кандидатов.
5. Загрузка hip-модели проверяет размер входа и решётки признаков; неподходящая область не отправляется в hip-инференс.
6. `workflow_profile.py` проверяет код и все модели в одном месте для CLI и API. Переменные моделей меняются только после успешной проверки всех компонентов. API readiness, одиночный анализ и пакетная сводка показывают идентификатор выбранного профиля.

Маски, предложения ROI и геометрические кандидаты сохраняют `clinical_validation=false`. Эти изменения исправляют программные измерения и происхождение результатов; они не придают модели подтверждённую клиническую точность.

## Состояние требований

Сверка выполнена с исходным `4. ДепЗдрав.pdf`, прежде всего §2.2–2.5 и §3.2. Различаются наличие алгоритма, программная проверка и доказательство его точности.

| Требование | Работающий путь | Проверка и предел |
|---|---|---|
| DICOM, несколько изображений, область и сторона | Чтение технических тегов, маршрутизатор по пикселям, отдельное зеркальное представление левого бедра | Проверки ошибочных файлов, неопределённой области/стороны, многокадрового ввода; низкая уверенность не превращается в диагноз |
| Проекция | Классификатор по пикселям и геометрический кандидат, метаданные как дополнительный сигнал | Unknown при неоднозначности; клиническая точность на всех устройствах не установлена |
| Охват позвоночника, Th12 и гребни | Критерий качества, обученные нумерованные маски, кандидаты гребней | Th12 не присваивается простым счётом от края; гребни не имеют подтверждённой точности |
| Ось позвоночника, предел 5° | Измерение в физических координатах, известные повороты и существующие экспертные метки | Проверены разные PixelSpacing и отсутствие измерения; несогласие геометрии и модели остаётся причиной проверки |
| Артефакты и наложения | Обученный критерий и синтетические контрольные пары | Оценка на имеющихся реальных метках; синтетические предметы не являются экспертной разметкой имплантов |
| Бедро: вертелы, шейка, седалищная кость, ротация | Критерии качества, костные маски, маска ROI шейки, эвристические ориентиры и 3D-контроли | Устойчивость эвристики исправлена; отдельная точность вертелов и седалищной кости не доказана; относительный угол CT не является клинической меткой укладки |
| ROI и поля 30/30/20 мм | Разбор явных ROI, точное сравнение масок, предложения переноса и ROI | Назначение ROI учитывается; отсутствие исходной ROI — неприменимость проверки исходной разметки. Перенос не меняет форму ради прохождения порога |
| Несколько нарушений и таблицы | Бинарное качество, типы, CSV/XLSX, отдельные расширенные сведения и ошибки обработки | Типизация кандидата заполнена, но её чувствительность ниже базовой модели; конкурсный контракт проверяется отдельно |
| Дополнительные DICOM и объяснения | PNG/JSON, SC/SR с ссылками на исходное изображение | Проверяются наличие и связи; это не полная сертификация DICOM, исходные нестандартные UID сохраняются |
| Пакетный API и локальный контейнер | Один проверяемый профиль для CLI/API, очередь, история и сохранение оригиналов | Сквозные задания и неизменяемые автоматические результаты; отдельная экспертная ревизия не переписывает модель |
| Воспроизводимость и оценка | Зафиксированные зависимости, веса и код, разбиения по исследованиям/источникам, отчёты OOF и экспериментов | Уже просмотренные folds не называются новым независимым тестом; персональность пациентов AASCE не доказана |

Функциональные ветки перечислены и работают. `requirements_complete` и `anatomical_checks_complete` остаются false, потому что часть анатомических проверок основана на кандидатах. Это не блокировка запуска и не требование добыть новые метки; это предел текущего доказательства качества. Полное закрытие клинических критериев здесь не заявляется.

## Сборка и запуск

Из корня проекта:

```bash
competition/run_profile.sh batch \
  data/specialists/runs/no-new-labels-runtime-v5-20260926 \
  '/путь/к/DICOM' '/путь/к/результатам'
```

Скрипт собирает образ из текущего репозитория, проверяет профиль при запуске и формирует таблицы, PNG/JSON и SC/SR в подкаталоге `results`. Вход и профиль монтируются только для чтения. Пакетный запуск работает с `--network none`, 4 CPU и 4 ГБ памяти. Нужны Bash, Docker и `realpath`.

Для локального интерфейса и HTTP API:

```bash
PORT=8000 competition/run_profile.sh api \
  data/specialists/runs/no-new-labels-runtime-v5-20260926 \
  '/путь/к/DICOM' '/путь/к/рабочему-каталогу'
```

API публикуется только на `127.0.0.1`. В контейнере каталог входа — `/data/in`; пакет можно отправить через `POST /api/v1/batch/path` с `{"input_path":"/data/in"}`. Для существующего процесса API достаточно задать абсолютный `DXAQC_WORKFLOW_PROFILE` перед стартом: три отдельных пути к моделям больше не обязательны. При неверном SHA-256 readiness не проходит и инференс не начинается.

Дополнительный CLI проверки `verify_workflow_api.py` запускает настоящий ASGI-конвейер: readiness → пакетное задание → скачивание результатов → сверка всех входных путей → повтор прогнозов → SC/SR. В тестовом контейнере он работает без сетевого доступа через TestClient; проверяет API-маршруты и worker, а не сетевую конфигурацию внешнего reverse proxy.

## Результаты проверки текущего профиля

Пакетный API внутри контейнера без сети, с ограничениями 4 CPU/4 ГБ, обработал **499 DICOM из 100 исследований: 499 Success, 0 Failure**. Получено 157 положительных результатов, все имеют тип нарушения. Классы качества, типы и вероятности совпали с ранее проверенным v2 на всех изображениях.

Независимый список всех входных путей совпал с расширенной таблицей. Конкурсная таблица, время обработки и SC/SR-ссылки проверены для всех 499 изображений. Время самой пакетной обработки и публикации — **260,475 с**, пиковая RSS — **572 268 544 байт**, максимальная верхняя граница времени одного исследования с общими расходами — **44,680 с**. Время очереди, предварительного сохранения исходного архива и скачивания ответов в эту пакетную метрику не входит. Это замер на данной машине, не на H200.

Проверка одиночного API подтвердила точное число пикселей в возвращаемых масках на трёх DICOM. Скрипт `run_profile.sh` реально собрал и запустил профиль на трёх DICOM; CSV и SC/SR прошли проверку. Повторная попытка писать в тот же каталог `results` отклоняется до запуска Docker. Для нового пакетного запуска выбирайте новый выходной каталог; рабочий каталог API может сохранять историю разных заданий.

Проверки проекта: frontend — 52 теста, lint и сборка; backend — 53 passed/2 skipped; конкурсный модуль после исправлений — **259 passed/5 skipped**. Пропущенные проверки не считаются доказательством качества. `git diff --check` и синтаксис shell-скрипта проверены.

Образ: `osseo-no-new-labels:runtime-v5`, digest `sha256:617aea7565b7aeb0f0c2b2691979b12d67d1bf24e1a1f4bbe2b12ce876c95172`. `run_profile.sh` собирает тот же код под локальным тегом `osseo-workflow:local`; целевой профиль проверяет код и веса при каждом старте. Машинный итог: [runtime_workflow_v5_2026_09_26.json](../competition/reports/runtime_workflow_v5_2026_09_26.json).

Общее количество технических флагов нестабильности бедра осталось 148: исправление не обещает улучшение клинической метрики, оно устраняет сравнение разных методов и уточняет происхождение точек.
