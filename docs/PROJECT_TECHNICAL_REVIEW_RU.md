# Техническая проработка конкурсного проекта

Проверено 17.09.2026 по исходному коду. Дополняет [очередь работ](HACKATHON_EXECUTION_RU.md); предлагаемые API и будущие компоненты ниже не объявляются реализованными.

## Данные и обучение

Теперь есть последовательность `competition_data → image_review.csv → competition_review → кандидаты меток`. Проверка не угадывает сторону по имени CR-файла и не исправляет клинические оценки. Для mapped сохраняется исходная оценка, для reviewed — новая вместе с исходной, пропуски остаются неизвестными. Спорная привязка нескольких изображений к одной области требует разбора. Проверка фактической таблицы: 252 pending, ни одной готовой связи.

Следующий компонент — фиксирование групп и разбиения после разбора похожих исследований. Записывать group_id, fold, источники связей и хеш версии меток отдельно. Не переносить черновой candidate_fold в обучение автоматически. Один patient ID `Anonymized` не даёт групп пациентов. Экспорт для оценки должен соответствовать именно удержанным вне обучения изображениям, а не всей тренировочной выборке.

Контракт будущей модели: вход — полный монохромный кадр с сохранёнными пропорциями и параметрами нормализации; выход — область/сторона, вероятность качества, вероятности применимых нарушений, необязательные ориентиры с признаками видимости. Конфигурация определяет preprocessing, порядок классов, пороги, версии правил; веса проверяются по SHA-256. В инференсе нет сетевых загрузок, оптимизации порога или обращения к Excel.

Интерфейс будущего адаптера отделить от существующего total-body: он возвращает конкурсные классы, а не преобразует эвристический UI-score в вероятность. При неизвестной области или отсутствующей профильной модели результат должен явно указывать невозможность оценки. Модель для левого и правого бедра может разделять параметры; сторона хранится отдельно и подтверждается данными.

## DICOM: найденное и исправленное

В `preprocessing.py` устранён молчаливый выбор первого кадра массива. До pixel_array теперь проверяются NumberOfFrames=1, положительные размеры, предел 16 миллионов пикселей и MONOCHROME1/2 с одним каналом. После декодирования форма должна совпасть с заявленной. Нефинитные значения отклоняются. Во внутренние metadata добавлен исходный SOPInstanceUID для будущего построчного экспорта.

Ограничение в 16 миллионов пикселей — инженерный предел текущего обработчика, не требование ТЗ. Многокадровый файл сейчас явно неподдерживаемый: если организатор включит такой формат, понадобится разбор кадров и уточнение количества строк результата. Ограничения декодирования не заменяют лимит размера HTTP-запроса и ограничение памяти процесса.

Нормализация пока процентильная, как в существующем сервисе. Для конкурсной модели сравнить её с сохранением исходного диапазона на обучающей части; не допускать удаления контрастных артефактов. `content_bbox` не использовать для автоматической обрезки, поскольку границы кадра важны для оценки охвата. Угол укладки и Cobb angle не смешивать; физические расстояния без масштаба не выдавать.

## Пакетный контракт: следующее изменение

Существующий `/api/v1/studies/analyze` обрабатывает один файл и применяет только готовый total-body маршрут. Конкурсный endpoint ещё не реализован. Предлагаемый первый вариант: синхронный `POST /api/v1/competition/analyze-batch`, multipart ZIP, ответ ZIP с `results.csv`, `diagnostics.jsonl` и `run.json`. Для больших пакетов перейти к job-id только если измерения покажут необходимость; заранее очередь задач не требуется.

`results.csv` — восемь рекомендуемых ТЗ полей, точные значения и разделители типов согласуются с организатором. Внутренние вероятности и технические причины хранятся отдельно, чтобы не менять внешний контракт без согласования. `diagnostics.jsonl` содержит относительный путь, код ошибки, версию модели и диагностические сведения без ненужных персональных тегов. `run.json` — число входов/успехов/ошибок, полный wall time, версии и хеши.

Обрабатывать каждую подходящую запись, не останавливаться после трёх физических файлов. Один исходный файл даёт одну строку по рабочему контракту; точные повторы можно кэшировать, но строки и UID сохраняются. Для повреждённого файла UID могут быть недоступны — пустые поля и Failure с причиной, а не выдуманный идентификатор. Никаких Success с фиктивным quality_class при отсутствующих весах.

Не извлекать архив без проверки: лимиты размера загрузки, числа файлов, суммарного распакованного размера и отдельного изображения; запрет абсолютных путей, `..`, ссылок, дублированных нормализованных имён и вложенной рекурсивной распаковки. Результаты и временные файлы привязаны к одному запуску; очистка в finally. Существующий RAR-importer Hologic — отдельный формат и не готовый ZIP endpoint для конкурса.

Матрица интеграционных проверок: чистый пакет; чистый + повреждённый; повторные пиксели с разными UID; неизвестная область; отсутствие весов; пустой архив; Unicode-пути; попытка выхода за каталог; лимит распаковки; повторный запуск. Приемка: число выходных строк соответствует объявленной политике, ошибки остальных файлов не скрыты, исходные UID не заменены UI-псевдонимами.

## Поставка и воспроизводимость

В проверенном `backend/Dockerfile` устанавливается базовый `pyproject.toml`. В этом составе нет PyTorch/MMPose и checkpoint, а Compose не монтирует модель. Контейнерная основа поэтому не является готовой поставкой нейросетевого инференса. Финальный образ для spine/hip должен явно содержать выбранный runtime, профильные веса/конфигурации и проверяемый model-ready статус. Не тянуть MMPose в новую поставку, если выбранной конкурсной модели он не нужен.

Базовые Docker-теги `python:3.11-slim`, `node:22-alpine`, `nginx:1.27-alpine` не зафиксированы digest. В Python зафиксированы прямые зависимости, а backend теперь имеет uv.lock; runtime-образ конкурса сохраняет отдельный проверенный requirements-lock. Во frontend используется pnpm-lock и frozen install, хотя package.json содержит `latest`: обновлять зависимости следует отдельным проверенным изменением lock-файла. GPU-профиль фиксировать после smoke-test на 5090, затем отдельно проверять инференс на доступной аналогичной целевой среде. Тестирование реальной H200 не заявлять до доступа к ней.

`/health` проверяет доступность процесса и наличие checkpoint, но не доказывает рабочий профильный инференс. Для финальной поставки нужны отдельные признаки process-ready и competition-model-ready; API не должен показывать успешную готовность модели лишь по наличию файла. CLI инференса и API должны вызывать одну реализацию, чтобы избежать расхождения результатов.

## Интерфейс и демонстрация

Текущий интерфейс, работа с total-body и динамикой BMD полезны как основа продукта, но не закрывают клинические критерии spine/hip. Следующая интеграция UI должна показывать режим технической проверки отдельно от результата профильной модели, количество обработанных/ошибочных файлов, причину Failure и скачивание конкурсной таблицы. Не выводить общий «качественно» по технической успешности чтения DICOM.

Приоритет интерфейсной работы после API: пакетная загрузка → прогресс/результат → список нарушений → доказательные ориентиры → экспорт. Динамика BMD, дополнительные панели и новые визуальные эффекты не являются ближайшей зависимостью конкурсной сдачи. Исторические примеры ответов с validated-model не считать текущими результатами сервиса.

## Порядок дальнейшей реализации

1. Заполненная таблица → проверка → разбор замечаний; параллельно подготовить ПК и пакетный контракт.
2. Зафиксировать группы и версию меток; обучить первый image-level вариант на 5090.
3. Подключить профильный адаптер к одному CLI/API-контуру, выполнить интеграционные проверки пакета.
4. Сравнить модели и внешние источники на неизменных группах; заморозить модель и пороги.
5. Собрать автономный образ с весами; проверить скорость и повторяемость, затем завершить UI и демонстрацию.

В этой итерации реализованы проверка экспертного CSV и усиление DICOM-подготовки. Пакетный endpoint, профильный адаптер и финальный образ остаются следующими работами, а не скрыто выполненными пунктами.

Проверки после изменений: `scripts/verify.sh` завершился успешно — lint, 23 frontend-теста, production-сборка и 48 backend-тестов. Через обновлённый `prepare_dicom` повторно обработаны все 499 обучающих DICOM без ошибок; исходный image_uid извлечён у каждого. Это подтверждение совместимости чтения, не клиническое качество модели. GPU и финальный Docker-инференс в этой проверке не запускались.
