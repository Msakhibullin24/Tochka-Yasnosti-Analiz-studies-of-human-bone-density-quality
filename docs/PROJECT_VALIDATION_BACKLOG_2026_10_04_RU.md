# Дополнительный аудит проекта и приоритеты доработки

Дата: 4 октября 2026 года. Проверены исходники, сохранённые экспериментальные данные и контейнер выпуска 1.11.6. Этот документ дополняет [архитектуру ансамбля](EVIDENCE_ENSEMBLE_ARCHITECTURE_2026_10_04_RU.md) и [спецификацию арбитра](ENSEMBLE_IMPLEMENTATION_SPEC_2026_10_04_RU.md).

Главный вывод: проекту требуется укрепить связь между измерением, полнотой проверки и формулировкой результата. Успешный запуск моделей ещё не подтверждает пригодность исследования или возможность интерпретировать динамику МПК. Помимо новых энкодеров, наибольшую пользу дадут независимая анатомическая разметка, проверка устойчивости измерений, сквозные контракты отчётности и испытания отказов.

## Выполненные проверки

- Полный `scripts/verify.sh`: lint, TypeScript, production build, 74 теста интерфейса, 53 теста исследовательского backend и 395 тестов основного backend прошли. Семь проверок пропущены; они не считаются выполненными.
- После исправления исследовательских импортов повторный полный основной набор дал 396 passed и 5 skipped. Ранее пропущенная проверка роутинга на трёх DICOM организатора отдельно включена через `DXAQC_DEBUG_SET` и прошла. Всего после исправления подтверждены 524 разные проверки; остаются шесть пропусков: два из-за отсутствующих torch/sklearn в исследовательском backend, один из-за matplotlib и три из-за версии transformers ниже требования GPU-окружения. Дополнительный целевой набор дал 39 passed и 3 skipped; повторные проверки не прибавляются к общему числу.
- Контейнер `osseo-dxaqc:1.11.6` с image ID `sha256:f052f998769029a0946cd9ed43afde99a1ea584c59dcadddfa4c4f7836bcaa2b` обработал 499/499 исходных DICOM без Failure. Независимый аудит подтвердил полноту входа, строгий CSV, таблицы, полное время и проверяемые ссылки дополнительных SC/SR. Это не полная DICOM-conformance проверка.
- По 11 сравниваемым медицинским полям все 499 ответов совпали с предыдущим сохранённым прогоном финального образа. Сравнение не использует время как медицинское поле.
- Три тестовых DICOM дважды обработаны тем же image ID: медицинские поля совпали на 3/3, ZIP дополнительных серий совпал побайтово. У этих трёх файлов нет ключа ответов, поэтому это проверка повторяемости, а не точности.
- Стресс-проверка геометрии повторена на 249 размеченных изображениях. Контролируемые сценарии отдельно проверили неполную анатомию в динамике, внутренний сбой API, вывод неопределённого типа в карточке и ограничение манифеста по расширению.
- Все 37 закреплённых файлов кода текущего профиля совпали с хешами паспорта. Инференс и медицинские веса не изменены.

Локальный полный пакет занял 161,902 с; консервативная верхняя граница на исследование — 42,086 с; пик RSS процесса — 508 121 088 байт. Это замер на общей локальной CPU-машине, не изолированный нагрузочный тест и не H200. Он не подтверждает время нового GPU-ансамбля.

Агрегированные доказательства находятся в [машинном отчёте](competition/project_validation_2026_10_04.json). Подробные логи и результаты DICOM сохранены локально в `data/project-audit-20261004/` и не добавляются в Git.

## Воспроизведённые проблемы

### Карточка исследования теряет положительный ответ без типа

В [ветке карточки исследования](../competition/dxaqc/api.py:512) пустая `violation_type` при `processing_status=Success` печатается как «Нарушений не выявлено». Контролируемый пример с `quality_class=1`, пустым типом и `violation_type_status=undetermined` воспроизвёл именно эту фразу.

Это расходится с `model_verdict` в `result_context.py`, где такой случай правильно называется выявленным нарушением без установленного типа. Обычный пакетный отчёт уже имеет защиту, но она не охватывает отдельную карточку исследования.

**Приоритет высокий.** Использовать один авторитетный генератор формулировки для всех отчётов. Добавить сквозной тест: один сохранённый положительный ответ без типа должен одинаково отображаться в карточке, пакетном отчёте, UI и экспортируемом описании. Обязательно проверить Failure и неполную анатомию. Изменение производственного API требует обновления закреплённого профиля выпуска, а не обхода его хешей.

### Анализ динамики не подтверждает условия сравнения МПК

В [модуле динамики](../competition/dxaqc/dynamics.py:102) сопоставимость зависит от бинарного QC и различий нескольких геометрических признаков. Не проверяются неопределённые критерии, полнота анатомии, соответствие исходных ROI и уровней, аппарат и происхождение LSC. API не запрашивает подтверждение принадлежности двух изображений одному пациенту.

В контролируемом сценарии с одинаковой геометрией, неопределённой осью, неполной анатомией, отсутствующей ROI и разными полями аппарата функция вернула `comparable` и назвала изменение МПК −6,7% значимым при LSC 3%. Флаг `tolerances_clinically_validated=false` присутствует, но не запрещает такую интерпретацию. Это проверка функции на заданных входах; не доказано, что она возникла на реальной паре пациентов.

Для количественного сравнения между аппаратами ISCD требует соответствующей перекрёстной калибровки; одного сходства укладки недостаточно. [Официальные позиции ISCD](https://iscd.org/text-based-official-adult-positions/).

**Приоритет высокий.** Разделить инженерную похожесть укладки и разрешение интерпретации динамики. Для второго нужен явный контекст: подтверждённая пара визитов, область и сторона, одинаковые анализируемые ROI/уровни, аппарат или подтверждённая перекрёстная калибровка, применимый LSC, полнота QC. При отсутствии контекста можно показывать геометрическое сравнение, но значимость МПК должна оставаться неопределённой. Валидировать маршрут на реальных повторных DXA после независимой экспертной оценки.

### Внутренний сбой сравнения не имеет структурированной причины

В [маршруте сравнения](../competition/dxaqc/api.py:589) обработан `DicomReadError`, но не общий сбой модели. Инъекция `RuntimeError` дала для `/analyze` структурированный JSON Failure, а для `/compare` — HTTP 500 с `text/plain` и «Internal Server Error».

**Приоритет высокий для устойчивости API.** Ввести общий контракт ошибок чтения, инференса и формирования результата; сохранить причину и этап, не возвращать частичное сравнение как Success. Проверить первый и второй визит, сбой загрузки весов, сбой анатомии и сериализацию результата. Не маскировать такие ошибки медицинским нарушением.

### Исследовательское обучение зависело от порядка тестов

Полный набор тестов проходил, но отдельный запуск `test_gpu_research.py` выявил `ModuleNotFoundError: verify_metric_candidate`. Причина: исследовательские модули импортировали соседние файлы без имени пакета; другой тест временно делал эти импорты доступными через `sys.path`.

**Исправлено в исходниках.** Импорты в `nested_criterion_upgrade.py` и `verify_metric_candidate.py` переведены на `experiments.*`. В `test_gpu_research.py` добавлен запуск трёх CLI с `--help` в чистых subprocess из постороннего каталога. Это защищает фактический запуск GPU-инструмента, а не только импорт в уже подготовленном процессе. Исправление исследовательское; существующий контейнер медицинского выпуска не пересобирался.

### Аудит поставки рассчитан только на файлы dcm

[Независимый манифест](../competition/audit_delivery.py:34) собирает только `.dcm`. Загрузчик поддерживает также другие DICOM-подобные расширения и файлы без расширения. Контролируемая папка с `.dcm` и `.dicom` даёт манифест на один файл.

**Приоритет средний.** Текущий аудит корректно применён к папке организатора, где все 499 входов имеют `.dcm`. Для универсальной проверки нужен явно заданный контракт входа: либо ограничить аудит этим форматом, либо независимо собирать манифест всех поддерживаемых файлов. Не брать манифест из результата, иначе пропущенный файл останется незамеченным.

## Что показали испытания измерений

В 198 синтетических поворотах позвоночника на ±7° ошибка эквивариантности была не выше 0,857°. При этом 9 из 10 реальных положительных меток оси по-прежнему имеют измеренный угол ≤5°. Алгоритм может воспроизводимо следовать повороту изображения и одновременно неверно выбирать анатомическую ось. Эти два свойства необходимо проверять разными эталонами.

При преобразовании яркости `clip(1.1*x−3)` на 150 изображениях бедра:

- на 15 изображениях выступ малого вертела изменился более чем на 5 мм;
- 95-й перцентиль изменения составил 16,789 мм;
- на трёх изображениях угол диафиза изменился более чем на 1°.

Это технический стресс-сценарий, а не оценка клинической ошибки в мм. Но зависимость ориентира от яркости требует проверки до использования в ротации и динамике. Нужно сравнить координаты до и после преобразования, установить ошибку сегментации и проверить альтернативную локализацию. Одна лишь оценка общей метки QC не обнаруживает такие дефекты.

У всех 150 изображений бедра отсутствует поддерживаемая исходная ROI, включая семь положительных меток текущего типа ROI/охвата. Следовательно, эту выборку нельзя использовать как доказательство точности проверки операторской ROI шейки. Нужны реальные исходные ROI с происхождением и отдельная разметка охвата сканирования.

## Незакрытые требования и следующие испытания

| Направление | Что требуется проработать | Проверяемый результат |
|---|---|---|
| Ось позвоночника | Независимые углы, выбранный участок, пригодность ориентиров | Ошибка и смещение угла, решения у 5°, интервалы на новых исследованиях |
| Видимость анатомии | Th12, оба гребня, структуры бедра; различать обрезку и ошибку локализации | Чувствительность видимости каждой структуры и доля неопределённых случаев |
| Нумерация и ROI | L1–L4, межпозвоночные границы, исходная ROI шейки | Эталонные уровни и ROI, ошибки перестановок и положения |
| Проекция | Подтверждённый AP/lateral/unknown для бедра | Полная проверка роутинга до QC, ложный допуск неподдержанной проекции |
| Подтипы ротации | Недостаточная и избыточная ротация | Независимые подтипы и контуры малого вертела |
| Данные и метрики | Новые пациенты, дубликаты, происхождение меток, замороженный тест | Пациентское разбиение только при подтверждённых ключах; интервалы и все отказы |
| Вероятности и арбитр | Калибровка полного маршрута, зависимость ошибок | Вложенная оценка, Brier, риск при автоматическом допуске и доля пересмотра |
| Повторные исследования | Условия сравнения МПК и применимость LSC | Пилот на реальных парах без неподтверждённой интерпретации |
| Нагрузка | Общий бюджет batch/analyze/compare, очередь и резерв диска | Измерения при параллельных запросах, ограничение ресурсов и управляемый отказ |
| Восстановление | Сбой при публикации, отключение питания, отмена и длительный инференс | Нет ложного Success и потери экспертных версий; проверенный повтор и откат |
| Дополнительные DICOM | Проверка SC/SR внешним валидатором | Отчёт conformance с отдельным учётом невалидных UID исходных данных |
| GPU и упаковка | Реальные forward/backward, H200, недостающие зависимости | Отдельная CI-проверка GPU, фиксированный профиль и измеренное время нового ансамбля |

Параллельные HTTP-запросы `/analyze` и `/compare` запускают инференс через `to_thread`, а batch использует отдельный worker. Общего ограничителя инференса в просмотренном API нет. Это риск перегрузки, а не уже измеренный отказ. Нужны контролируемые прогоны на 1/2/4/8 запросах с фиксацией RAM, времени, отзывчивости readiness и сохранности очереди. Для очереди отдельно определить предельное число заданий и резерв диска: максимальный размер одного upload не ограничивает их совокупный объём.

Не расширять это испытание до PACS-интеграции: она не входит в текущую область проекта. Проверить сначала существующие локальные маршруты и экспорт.

## Как использовать вычислительные ресурсы с наибольшей пользой

Сначала построить корпус контрактных сценариев с контролируемыми ожидаемыми результатами: потеря тегов, полярность, разные масштабы X/Y, повреждение пикселей, переворот стороны, обрезка кадра, неизвестная проекция, частичный ROI, сбои модели и отчётности. Для каждого преобразования заранее задать, какое свойство сохраняется и какое должно измениться. Поворот и crop могут менять медицинскую метку.

Далее применить генеративное тестирование допустимых DICOM и mutation testing к узким критическим правилам: 5°, отступы 30/30/20 мм, unknown→pass, полный манифест, конфликт экспертных версий и публикация отчёта. Проверить, что тесты обнаруживают намеренно внесённые ошибки; увеличение количества тестов само по себе ничего не доказывает.

После получения эталонов — полный вложенный эксперимент с ансамблем и анатомией, сравнение одиночных моделей, простого среднего и stacking, аудит всех общих пропусков. На GPU отдельно проверить ошибки обучения, маски неизвестных меток и отсутствие данных внешнего фолда в калибровке. После выбора кандидата — один замороженный независимый тест и измерение целевого времени.

Текущая среда содержит CPU-сборку PyTorch 2.1.2; CUDA недоступна, `nvidia-smi` не связался с драйвером. Поэтому реальное обучение на GPU и H200 здесь не выполнено. Большие вычислительные ресурсы полезны для экспериментов, но не заменяют отсутствующие экспертные углы, ROI и независимых пациентов.
