# Самодостаточный Osseo AI: проект продукта и порядок реализации

Дата: 19.09.2026. Статус: проект решения, функции ниже не следует считать реализованными. Основание — аудит `COMPETITION_READINESS_AUDIT_2026_09_19_RU.md`, конкурсный код и существующие инструменты разметки в старом приложении. Это план конкурентоспособного продукта; превосходство над участниками без сравнительного теста не установлено.

## Целевой результат

Специалист локально загружает исследования, видит полноту обработки, открывает подозрительные места, проверяет измерения, исправляет предложенную разметку, подтверждает результат и получает связанный с исходными изображениями отчёт. После перезапуска всё сохраняется. Организатор запускает тот же анализатор из CLI/API и получает стабильный конкурсный CSV без ручного участия команды.

Главное отличие, которое следует доказать: каждое обнаруженное нарушение сопровождается проверяемым основанием и доступным действием специалиста. Необходимы одновременно качество обнаружения, завершённый рабочий процесс и независимый запуск.

## Функции и проверяемые условия готовности

| Приоритет | Блок | Что реализовать | Как принимаем |
|---|---|---|---|
| P0 | Надёжный приём | DICOM/папка/ZIP, инвентаризация входа, прогресс, причины исключений, частичный результат | Ни один повреждённый или пропущенный вход не исчезает; CLI/API дают согласованные результаты и ошибки |
| P0 | Единое решение | Общая обработка порогов, правил, неизвестных критериев и официальных меток | CV, CLI, API, UI и экспорт используют одну версию решения; нет порога 0.5, заданного отдельно в UI |
| P0 | Геометрия | Масштабы X/Y, ориентация, достоверность масштаба, корректный ключ кэша | Перестановка файлов не меняет результат; одинаковые пиксели с разным масштабом не получают чужие измерения |
| P0 | Установка и хранение | Один локальный запуск, сохранение заданий, проверка модели и доступного места | Запуск на чистой машине; перезапуск не теряет результаты; резервная копия восстанавливается |
| P1 | Рабочий список | Исследования и изображения, поиск, фильтры по области/типу/статусу проверки, переход к следующему | Специалист обрабатывает смешанный пакет без ручного поиска файлов; большие списки загружаются постранично |
| P1 | Просмотрщик | Исходное изображение, включаемые слои, масштабирование/перемещение, измерения, несколько изображений исследования | Преобразования экрана не меняют исходные координаты; можно сравнить оригинал и результат |
| P1 | Объяснение | Критерий → локализация → измерение/источник → основание вердикта → действие для проверки | Отсутствующее измерение показывается как недоступное; объяснение не выдаёт корреляционный признак за измеренный факт |
| P1 | Проверка специалистом | Подтвердить/исправить/оставить неоценимым, комментарий, сохранение черновика и финальной версии | Исходный вывод ИИ неизменяем; сохранены автор, время и причина; конкурентное редактирование не затирает изменения |
| P1 | Редактор ориентиров/ROI | Перемещение точек и границ, отмена/повтор, сравнение до/после, отдельное подтверждение | Исправления сохраняются в координатах исходника; из них пересчитываются соответствующие измерения |
| P1 | Итоговый комплект | Конкурсный CSV/XLSX, отчёт для просмотра/печати, PNG, SC/SR | Вердикты совпадают между форматами; производные DICOM ссылаются на правильный исходный объект |
| P1 | Улучшение модели | Перепроверка меток и ориентиров, честная оценка полного пайплайна | Прирост подтверждён заранее выбранным протоколом; показаны F1/AUC, пропуски, ДИ и поддержка редких классов |
| P2 | Динамика | Два подтверждённо сопоставленных визита, синхронный просмотр, явные ограничения сравнения | Разные пациенты/стороны/аппараты не объединяются молча; вычислительная логика отделена от неподтверждённых клинических допусков |
| P2 | Аналитика | Доли типов ошибок, очереди на проверку, исправления специалиста, время обработки | Отдельно статистика ИИ и подтверждённых результатов; дубликаты не раздувают показатели |
| P2 | PACS | Один выбранный для конкретного пилота способ приёма/выдачи | Сквозной тест с целевой системой, корректные ссылки и повторная доставка без дублей |

P0 — до финальной технической сдачи; P1 — законченный основной продукт; P2 — последующее развитие. Автономность достигается без обязательного PACS, внешней учётной записи и интернет-сервисов.

## Четыре основных экрана

1. **Исследования.** Загрузка, история пакетов, прогресс, ошибки, очередь проверки, выгрузка. Ошибка обработки и подозрение на нарушение качества отображаются раздельно.
2. **Проверка исследования.** Список изображений слева, изображение и слои в центре, критерии/основания справа, подтверждение и переход далее. Сначала показывается действие, затем детали расчёта.
3. **Результаты.** Подтверждённые заключения, версии и экспорт; можно восстановить, что именно посчитала модель и что изменил специалист.
4. **Состояние системы.** Версия модели и область её применения, диск, очередь, диагностика, резервное копирование. Инженерные сведения не перегружают экран специалиста.

Редактор открывается внутри проверки исследования. Отдельный исследовательский раздел для подготовки разметки и сравнения моделей не должен быть обязательным шагом обычного пользователя.

## Архитектура без второго конкурирующего продукта

Целевой основной runtime — существующий `competition/dxaqc`: его ядро используется CLI и одним FastAPI-приложением. Локальный worker обрабатывает задания. Для истории, версий и очереди на одной машине достаточно SQLite и файлового каталога артефактов; отдельные брокер сообщений и микросервисы сейчас не обоснованы.

Целевой UI — React-приложение, обслуживаемое тем же сервисом из собранной статики. Существующий конкурсный HTML остаётся рабочим до прохождения React полного сценария загрузка → проверка → экспорт, затем удаляется из основного runtime. Два интерфейса с независимо развивающимися правилами оставлять нельзя. Старый backend сохраняется как исследовательский инструмент до переноса нужных возможностей; конкурсный runtime не должен зависеть от него по сети.

| Уже есть | Использовать | Что требуется изменить |
|---|---|---|
| `competition/dxaqc` | Чтение, модель, пакет, экспорт, динамика | Общий контракт результата, корректность геометрии/ошибок, сохранение заданий |
| `src/App.tsx`, компоненты просмотра | Структура рабочего места, инструменты просмотра | Убрать демонстрационный поток из рабочего режима, подключить фактические конкурсные ответы |
| `src/DatasetWorkbench.tsx` | Механика редактирования и экспертной разметки | Выделить переиспользуемые компоненты; устранить привязку к формату Hologic-workbench |
| `backend/app/annotations.py` | Проверки координат, присутствия дефекта и экспертных данных | Явный адаптер к конкурсным идентификаторам и таксономии; не переносить старую схему целиком |
| `competition/ingest.py`, `review_candidates.py` | Подготовка кандидатов и очереди перепроверки | Импорт подтверждённых экспертных версий; защита контрольного набора |

На этапе перехода выбрать один явно названный источник результата. При недоступной модели UI показывает ошибку сервиса, а не подменяет её локальным pre-screening или демонстрационным ответом. Старый функционал total-body не маркируется как прошедшая проверку модель позвоночника/бедра.

## Контракты и состояние

Ввести версионированный внутренний результат с отдельными сущностями: входное изображение, запуск модели, оценка критерия, набор геометрии, экспертная редакция, задание экспорта. Существующие восемь конкурсных колонок и согласованный дополнительный score сохраняются как экспортный адаптер. Расширения API вводятся совместимо; старые маршруты поддерживаются на время перехода.

У критерия хранятся score, применённый порог, итог, возможность оценки, причина, ссылки на геометрию и версия правил. Отсутствие ориентиров или масштаба не превращается в отрицательный диагноз. Score ансамбля до проверки калибровки нельзя описывать как достоверную вероятность ошибки. Низкая уверенность роутера — сигнал для проверки, но высокая сама по себе не доказывает, что аппарат или проекция поддерживаются.

Вердикт ИИ, состояние обработки, состояние проверки человеком и исправленная разметка — разные поля. Человек может подтвердить результат или добавить новую версию; нельзя задним числом менять машинный CSV и выдавать его за автоматическое предсказание. Экспорт должен явно выбирать машинную либо экспертную версию.

Для заданий: queued → running → finished/partial/failed/cancelled. После перезапуска незавершённое задание обнаруживается и безопасно возобновляется либо повторяется с того же зафиксированного входа. Транзакционно резервировать задания одному worker; артефакты писать во временные файлы и публиковать атомарно. Отмена применяется на безопасной границе обработки файла. Удаление и срок хранения данных — явные действия/настройки, а не неожиданное удаление последних 50 заданий.

Геометрия: координаты исходного изображения, размеры, X/Y spacing, источник масштаба и преобразования ориентации. Просмотрщик применяет обратимые преобразования только при отображении. Изменение версии схемы SQLite сопровождается миграцией и проверкой восстановления резервной копии.

## ROI: три разные функции, которые нельзя смешивать

1. **Контроль охвата снимка.** Текущая основа: хватает ли анатомии для анализа.
2. **Предложение разметки.** Модель предлагает ориентиры/ROI, специалист может исправить и подтвердить. На первом этапе допустим ручной редактор с честно обозначенными эвристическими подсказками.
3. **Проверка существующей разметки.** Необходимо получить и разобрать реальные линии/контуры или другие объекты разметки и оценить их относительно анатомии. Отсутствующая разметка означает «не предоставлена», а не «корректна».

Сначала согласовать ожидаемый вход с организатором. Обучение точного локализатора требует экспертных ориентиров и протокола неоднозначных случаев; редактор сам по себе этот пробел не закрывает. Автокоррекция публикуется как предложение, исходный DICOM не переписывается, BMD из изменённой картинки не выдумывается.

## Где оптимизировать модель и скорость

В модели сначала устранить расхождение оценки и инференса, затем работать над ротацией бедра и осью позвоночника. Разметить пилотную подвыборку ориентиров с независимым повторным чтением, измерить согласие экспертов и время разметки; по результату оценить объём остального набора. Фиксированную архитектуру новой сети до этого выбирать преждевременно. Кандидаты — улучшенные измерения и небольшой обучаемый локализатор с тем же downstream-классификатором. Каждый сравнивать с текущим baseline на одинаковых разбиениях.

Протокол эксперимента фиксировать заранее: основные F1/ROC-AUC, метрики каждого типа и области, допустимые регрессии, отдельные пороги во внутренней CV. Держать независимый контроль; повторный выбор признаков по всем фолдам не становится независимой проверкой от наличия bootstrap. Экспертные исправления не стирают исходные метки: хранить обе версии и раздельно показывать результаты против конкурсной и уточнённой разметки.

По скорости текущий полный прогон 499 файлов занял 82.9 с, максимум 4.51 с/исследование: ускорение не является главным ограничением. Измерять отдельно декодирование, эмбеддинг, геометрию и экспорт. В `Analyzer.analyze` для spine/right hip можно повторно использовать эмбеддинг роутера, поскольку пиксели не зеркалились; для левого бедра второй эмбеддинг нужен. Прежде оптимизации кэша исправить его семантический ключ. Затем, только по профилю, рассмотреть пакетное извлечение эмбеддингов и ограниченное параллельное декодирование. Не добавлять GPU или ONNX без измеренной пользы и проверки эквивалентности.

## Самостоятельное развитие и поставка

Подтверждённая разметка экспортируется в версионированный обучающий набор; обучение запускается отдельно, выпускает кандидата, сравнение с baseline и воспроизводимый отчёт. Новый кандидат не заменяет рабочие веса автоматически. Поставка модели включает хеши весов/кода/данных, конфигурацию, метрики, область применимости и возможность отката.

Комплект сдачи: исходники, собранный образ для переноса без сети, все веса, скрипт запуска, пример входа без чувствительных данных, ожидаемая структура результата, инструкция, отчёт испытаний и слайды. Проверка готовности сервиса должна загружать модель и проверять запись данных; одного HTTP 200 недостаточно. На локальном однопользовательском старте — loopback; сетевой многопользовательский режим требует аутентификации и ограничения доступа до подключения реальных пользователей.

Достаточная демонстрация: смешанный пакет → полнота/ошибки → найденное нарушение с основанием → исправление ориентиров → подтверждение → экспорт → перезапуск и сохранённая история. Отдельно показать известный пропуск модели и неизвестный вход. Научная часть защиты: честные метрики и сравнение вариантов; продуктовая — этот завершённый процесс.

## Последовательность реализации и зависимости

1. **Надёжное ядро:** исправления аудита, единое решение CV/inference, контейнерная приёмка, актуальная документация. Готово при согласованных результатах и корректном отчёте на нормальных/повреждённых входах.
2. **Сохранение и общий UI:** внутренний контракт, SQLite/артефакты, адаптер API, рабочий список и просмотрщик. Готово при сквозном сценарии и восстановлении после перезапуска.
3. **Экспертный цикл:** ориентиры/ROI, версии, подтверждение, отчёты, экспорт разметки. Готово при сохранении исходного ответа ИИ и воспроизводимом пересчёте исправленных измерений.
4. **Качество и доказательства:** экспертные данные, локализатор-кандидат, независимая оценка, измерение полезности объяснений. Сбор экспертных данных можно начать одновременно с этапом 2, обучение зависит от утверждённого протокола.
5. **Пилотные расширения:** динамика, аналитика и конкретный PACS-коннектор после приёмки основного цикла.

Для календарной оценки нужны дата финала, доступность эксперта и объём согласованной разметки. До этого корректнее управлять по условиям завершения этапов. Доказательство готовности — успешно пройденные сценарии и измеренное качество, а не число реализованных экранов.
