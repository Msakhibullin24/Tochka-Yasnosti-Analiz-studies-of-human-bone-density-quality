# Карта проекта

Этот файл — короткая точка входа в репозиторий. Он фиксирует, какие части являются
исходным кодом, какие — локальными данными, и какой режим запуска считать основным.

## Основные режимы

| Режим | Исходники | Для чего нужен | Запуск |
| --- | --- | --- | --- |
| Конкурсный DXA QC | `competition/` | Основной локальный анализатор DICOM позвоночника и бедра | `./competition/run.sh build` и `./competition/run.sh serve 8090` |
| Исследовательский workbench | `src/`, `backend/`, корневые `Dockerfile` и Compose | Эксперименты с total-body/Hologic, датасетами и longitudinal-анализом | `make dev` или `docker compose -f docker-compose.research.yml up --build` |
| Пакетная обработка | `competition/run.sh`, `competition/dxaqc/` | Обработка ZIP без веб-интерфейса | `./competition/run.sh batch INPUT.zip OUTPUT_DIR` |

Конкурсный режим — источник истины для текущего пользовательского продукта. Старый
workbench сохраняется для исследований и не должен незаметно менять контракт конкурсного
анализатора.

## Что где находится

### Исходный код и проверяемые артефакты

- `competition/dxaqc/` — runtime, API, DICOM/QC-логика и хранение пакетов.
- `competition/tests/` — тесты конкурсного runtime и API.
- `competition/models/` и `competition/weights/` — проверяемые release-веса конкурсного режима.
- `competition/run.sh` — единая точка входа для Docker-сборки, тестов, сервиса и batch.
- `src/` — React-интерфейс исследовательского режима.
- `backend/app/` — FastAPI и исследовательские модули старого workbench.
- `backend/tests/` — тесты исследовательского backend.
- `scripts/` — воспроизводимые команды разработки, проверки и обучения.
- `docs/` — продуктовая, исследовательская и эксплуатационная документация.
- `competition/docs/` — документация, относящаяся именно к конкурсному runtime.

### Данные и локальные результаты

| Путь | Статус | Правило |
| --- | --- | --- |
| `data/` | Локальное хранилище, полностью ignored | Не коммитить. Здесь могут быть PHI-чувствительные данные, веса, кэши и результаты запусков. |
| `datasets/` | Исходные/внешние архивы, часть уже tracked | Не удалять и не перемещать без отдельной проверки ссылок и лицензий. |
| `competition/out/` | Рабочие результаты конкурсного runtime | Можно очищать после проверки, не является исходным кодом. |
| `data/runtime/` | Постоянные runtime-данные Compose | Сохранять при необходимости восстановления истории. |
| `data/specialists/` | Локальные specialist-веса, эксперименты и отчёты | Не коммитить автоматически; публиковать только отдельный проверенный release-артефакт. |
| `runs/` | Результаты локальных YOLO/ML-запусков | Generated; безопасная очистка выполняется через `make clean-generated APPLY=1`, если там нет нужных файлов. |
| `dist/`, `node_modules/`, `**/__pycache__/`, `.pytest_cache/` | Кэш/сборка/зависимости | Не являются частью проекта и не должны попадать в Git. |

Большой локальный checkpoint `backend/models/checkpoint.pth` намеренно ignored;
его контрольная сумма хранится в `backend/models/checkpoint.sha256`. Это позволяет
не раздувать репозиторий бинарником и одновременно проверять загруженный файл.

## Команды первого уровня

```sh
# Полная проверка frontend, обоих backend и конкурсного контейнера
make verify

# Быстрая проверка доступности локального сервиса
make smoke

# Безопасно показать generated-пути, которые можно очистить
make clean-generated

# Применить очистку только к кэшам и сборочным результатам
make clean-generated APPLY=1
```

Для specialist-моделей команды `make specialists`, `make train-specialists` и
`make advance-specialists` записывают результаты в `data/specialists/`; исходный
код при этом остаётся в `competition/` и `scripts/`.

## Проверка перед изменением границ проекта

Перед перемещением файла или удалением каталога нужно проверить ссылки:

```sh
rg -n "путь/к/файлу|имя/каталога" README.md docs competition backend src scripts Makefile
```

Не следует переносить исторические отчёты только ради красивого дерева: они уже
связаны ссылками и служат журналом решений. Для навигации используется этот индекс,
а не массовое переименование документации.

## Ограничения текущего продукта

Поддерживаемый конкурсный registry сейчас ориентирован на total-body; маршруты
spine/hip явно остаются неподдержанными до отдельной клинической валидации. Результат
требует проверки специалистом, а отсутствие внешней клинической валидации нельзя
устранить одной перестройкой каталогов или тестами.
