# План доведения решения до конкурсной сдачи

Состояние на 17.09.2026. Основной документ управления следующими работами; подробности моделей — в [плане экспериментов](MODEL_AND_DATA_DECISION_RU.md), данные — в [аудите](TASK_AND_DATASET_ANALYSIS_RU.md). Первое место не является проверяемым внутренним критерием: результат зависит от закрытого теста и соперников. Проверяем выполнение ТЗ, качество и воспроизводимость.

Пользователь решил хранить большие данные и обучать на ПК с RTX 5090. На ноутбуке продолжаем разработку, проверку контрактов и подготовку аннотаций. Дальнейшие загрузки больших наборов на ноутбук не планируются. Даты сдачи и доступ к ПК пока неизвестны; сроки ниже выражены этапами, не вымышленными календарными датами.

## 2. Метрики и правила их использования

В ТЗ приоритетны F1 и ROC-AUC; точная формула итогового балла не дана. Рабочие амбициозные ориентиры: F1 ≥ 0,90, ROC-AUC ≥ 0,95, чувствительность и специфичность ≥ 0,90. Это не прогноз, не достигнутые результаты, не официальный порог победы. После первого корректного image-level эксперимента оцениваем реалистичность ориентиров; не изменяем правила оценки ради красивых чисел.

Отчёт: общий результат и срезы по позвоночнику/правому/левому бедру; F1 положительного класса, ROC-AUC, AP, sensitivity, specificity, balanced accuracy, TP/FP/FN/TN и 95% групповые интервалы. AP явно называется average precision; не смешивать её с трапецеидальной PR-AUC. Классы без нужной поддержки получают `null` с числом наблюдений. Для редких нарушений абсолютные ошибки важнее десятых долей процента.

Отдельно: macro-F1 по утверждённым нарушениям с маскированием неизвестных меток, показатели каждого класса и его поддержка. Для нескольких одновременных нарушений — multilabel, а не выбор ровно одного класса. Позиционирование/ротация объединены в исходном Excel: отдельные ответы требуют дополнительных меток либо согласованной таксономии. Для масок — Dice/IoU; для ориентиров — ошибка координат; для оси — ошибка угла и ошибки решения вблизи 5°. Эти расчёты добавляются после появления эталонов, не имитируются.

Ошибки чтения, пропущенные результаты и неподдерживаемые входы учитываются в покрытии. Метрики на успешных файлах всегда подписываются как условные; это не итоговый балл по всем входам. Правило штрафа за Failure уточняется у организатора. Не заменять технический Failure клиническим классом 1.

Время: wall time всего исследования, включая чтение, подготовку, инференс и экспорт, p50/p95/max, отдельно холодный запуск. Лимит ТЗ — 180 секунд. Перестраховываемся проверкой худшего поддерживаемого случая; среднее время не доказывает соблюдение лимита. Время в строках CSV не заменяет инструментирование полного исследования.

Первые три пункта не требуют полной ручной сегментации всех кадров. При отсутствии любой новой разметки можно продолжить исследовательские модели уровня исследования, но нельзя назвать их выполнением image-level ТЗ. Приоритет нового экспорта через врача — реальные целевые ошибки и различные аппараты; наличие врача не означает разрешение на экспорт или наличие файлов.

## 4. Эксперименты без утечки

Сохраняем существующий реестр E00–E11 в `docs/competition/experiments.csv`. CPU study-level результат не отмечает image-level E01 выполненным. Для каждого запуска нужны: версия данных/меток/групп, версия кода, checkpoint/hash, seed, конфигурация, выбор эпохи/порога, OOF-предсказания, длительность и анализ ошибок.

Разбиение минимум по исследованиям, при наличии достоверного patient key — по пациентам. Все точные копии и подтверждённые связи удерживаются вместе. Число фолдов определяется поддержкой редких классов; пять фолдов не самоцель. Проверочные данные не участвуют в подборе порога, ранней остановке или корректировке модели. Внешнее предобучение использует только разрешённую обучающую часть источника; пересечения с независимым тестом исключаются.

Сначала ограниченное сравнение frozen encoder / дообучение / альтернативный encoder, затем один источник данных или одна анатомическая ветвь за эксперимент. Повторное сравнение по одним внешним фолдам уже адаптирует решение к ним: окончательное независимое подтверждение — новая выборка или закрытый тест организатора. Аугментации не должны устранять или создавать оцениваемый дефект без изменения метки.

## 5. Как пользоваться инструментом оценки

Используется среда с NumPy и scikit-learn из `backend/requirements-training.txt`. Эталонный CSV содержит:

```text
path_to_study,study_uid,image_uid,anatomical_region,quality_class,group_id
```

`quality_class`: 0, 1 или пусто для неизвестного. `group_id` — проверенная группа связанных исследований, а не одинаковый для всех `Anonymized`. Ключ строки — три поля path/study_uid/image_uid; пути в двух CSV должны совпадать точно. Срезы считаются по эталонной области, чтобы ошибка маршрутизации не скрывала трудные кадры.

Внутренний CSV предсказаний содержит восемь рекомендуемых ТЗ полей плюс `quality_probability`. Последнее поле необходимо для AUC; включение дополнительных колонок в финальный файл организатора согласуется отдельно. `Success` требует класса и конечной вероятности от 0 до 1. Для `Failure` эти поля могут быть пустыми. `violation_type` читается как поле контракта, но содержание типов нарушений текущий бинарный evaluator ещё не оценивает.

```bash
backend/.venv/bin/python backend/scripts/evaluate_competition.py \
  --truth data/evaluation/truth.csv \
  --predictions data/evaluation/predictions.csv \
  --output data/evaluation/metrics.json
```

Пути — пример ожидаемых будущих файлов, не утверждение об уже имеющемся эталоне. Скрипт не подбирает порог, использует переданный бинарный класс, сохраняет SHA-256 входов и не перезаписывает отчёт. Пропущенные строки учитываются как Missing, лишние/дублированные ключи отклоняются. Отдельно считаются покрытие, потерянные положительные/отрицательные примеры и точность области на успешных ответах. Групповой bootstrap описывает фиксированные предсказания, не неопределённость выбора архитектуры. Проверку train/test leakage этот скрипт не заменяет.

## 6. Пакетная поставка: что проверить

- Корректное исследование каждой области; несколько нарушений одновременно; пограничный наклон; необычная анатомия; отсутствующий масштаб; неизвестная сторона.
- Повторы с разными SOPInstanceUID; сохранение исходных UID даже при предупреждении о синтаксисе; больше трёх физических файлов из-за копий.
- Пустой архив, повреждённый DICOM, неподдерживаемое содержимое; отсутствие необработанных исключений и потери остальных строк.
- Защита распаковки от выхода за каталог, лимиты входа/пикселей; явное описание поддерживаемых форматов и исключений.
- Повторный запуск даёт те же классы; локальные веса и зафиксированные зависимости; отсутствие медицинских изображений в сторонних сервисах.
- Контроль полного времени на указанном оборудовании. Финальная конфигурация ТЗ — отдельная VM с одной H200 141 GB, 44 CPU, 256 GB RAM; две H200 не следует считать одной доступной двухкарточной машиной.
- Документы: модель/предобработка, формат API/результатов, минимальные ресурсы, запуск, обучение, ограничения, лицензии, ошибки и действия пользователя.

Клинические проценты оцениваем на отложенных данных, функциональные требования — отдельными интеграционными проверками. Ни интерфейс, ни наличие контейнера сами по себе не подтверждают качество модели.

## 8. Защита и финальное решение о готовности

Демонстрация: корректный кадр, наклон, артефакт, ротация, пограничный случай, повреждённый файл. Каждый пример помечен как обучающий или независимый. Показываем реальные вычисления; Grad-CAM подписывается как внимание модели, а не подтверждённая локализация нарушения. DICOM SR и автоматическая коррекция — дополнительные функции после обязательных.

Решение готово к сдаче, когда закрыты обязательные области/классы, все ограничения явно описаны, контрольный пакет проходит полностью, измерен лимит времени, получены честные метрики и контейнер независимо воспроизводится. Целевые 0,90/0,95 остаются ориентирами качества, а не заменой этих проверок. Слайды: задача → данные → разметка → модель → валидация → сравнение → ошибки → скорость → демонстрация → план пилота.
